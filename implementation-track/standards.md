# 实现跟踪规范（个人/团队风格标准）

本文件包含两个 profile。按项目文档结构选择，不要混用：`docs/00-README.md` + 00~05、07 用 Game profile；PRD + 各包 DESIGN.md 用 Software profile。

## Software profile

以下为默认偏好，其他团队可整体替换。

### 验收跟踪表位置

- 编号验收（如 M1-M20）状态汇总：PRD 的验收状态章节（执行视图，随实现更新）
- 包级验收状态：各包 DESIGN.md（就近工程，随包更新）
- 验收判定标准：对应论证文档末尾的验证清单

### 状态标记

语义见 `docs-core`。

◻ 未开始 / 🔄 进行中 / ✅ 通过 / ❌ 失败（附原因）

### 偏差记录格式

四段式：现象（可复现）→ 判断（违反哪条编号原则）→ 修复（实际改动）→ 回写（回写论证文档并带日期，或标注留待评审）

### 实现顺序参考（示例）

先确认包边界，再按依赖链实现。示例：核心引擎 → 工具/装配 → 适配层 → 全链路组装 → 前端壳。新功能先确认包边界再动手。

### 测试纪律

- 全库测试全绿才算验收通过
- **接口边界用最小 fake**：只实现接口的假对象也要能驱动消费者；如果必须依赖具体实现，说明边界没抽干净
- 测试/验证读真实配置的坑（本地配置可能含真实凭据）：配置目录必须指向临时位置（如显式 --agent-dir），防止泄露
- 文件操作（write_file）失败必须确认重写，不假定成功
- 真实厂商验证用临时 env 注入 key，验证后删除，不落命令历史

## Game profile

适用于 `game-docs` 的 `00~05、07` 文档结构（06 可选）。

### 验收跟踪表位置

- 状态汇总：`docs/03-acceptance.md` 的「验收跟踪」
- 验收判定标准：`docs/03-acceptance.md` 的 `AC-*` 用例
- 行为规则：`docs/02-design-spec.md` 的规则 ID
- 证据：`docs/05-reviews/` 的评审行动项与试玩结论

### 状态标记

语义见 `docs-core`。

◻ 未开始 / 🔄 进行中 / ✅ 通过 / ❌ 失败（附原因）

### 偏差记录格式

写入 `docs/03-acceptance.md` 的「偏差记录」，四段式：

现象（可复现）→ 判断（违反哪条 `AC-*` / 规则 ID）→ 修复（实际改动）→ 回写（回写 02/03 并带日期，或标注留待评审）

### 优先级

语义见 `docs-core`。

- 验收：`P0` / `P1`
- 功能 / 包：`High` / `Medium` / `Low`

**P0/P1 只表示验收优先级**，不要拿来排功能优先级。

### 测试纪律

- 固定种子必须可复现
- 每局日志包含：种子、结果、时长、统计、选择记录、压力/失败指标
- 性能测试记录机型 / CPU / GPU
- 全绿才算验收通过；部分覆盖标 🔄

### 证据阶梯

不同问题用不同证据，不能用低层证据替代高层结论：

| 层 | 回答 | 不能回答 |
|---|---|---|
| 静态预览 / 数据模型 | 数值、规则、展示是否自洽 | 实际手感、压力 |
| 真实模拟 / 受控压测 | 机制能否跑通、性能是否达标 | 真人是否觉得好玩 |
| 固定种子 + bot 回归 | 可复现性、压力/失败分布 | 学习曲线、乐趣 |
| 真人试玩 | 理解、乐趣、重开意愿 | 大规模平衡 |

### 可观测性

- 每局至少记录：种子、构筑、关键选择序列、压力指标、压力来源、失败时间、关键阶段状态
- 失败必须可归因；不能归因时先补观测，不凭感觉调数值
