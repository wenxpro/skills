# 实现跟踪（验收 + 偏差）

目标：每个验收项状态可查、每个实现偏差可追溯、设计文档与实现同步演进。

> 个人/团队偏好（验收表位置、状态标记、偏差格式）在 `standards.md`。

## 文档 profile

先判断项目使用哪套文档，不要混用：

| 文档结构 | profile | 验收基线 |
|---|---|---|
| `docs/00-README.md` + 00~05、07 | **game** | `03-acceptance.md` 的验收跟踪 + `AC-*` 用例 |
| PRD + 各包 `DESIGN.md` | **software** | PRD / DESIGN.md / 验证清单 |
| 不确定 | — | 先问用户，不要猜 |

本 skill 只更新状态与偏差，不改验收判定标准。

## 何时使用

- 开始实现一个验收项 / 完成一个验收项
- 实现中发现设计文档与实现冲突
- 汇报「做到哪了」「还剩什么」
- 版本收尾前核对验收清单

不适用：当前 Spec / 验收的创建（用 `game-docs`）、分期规划（用 `roadmap-planning`）、代码梳理（用 `code-digest`）、文档审核（用 `docs-audit`）。

## 操作顺序

1. 界定当前任务（对应哪个验收项）
2. 查验收基线
3. 实现与测试
4. 更新验收状态
5. 记录偏差（如有）
6. 汇报状态

## 第一步：界定当前任务

写下来：本次实现对应哪个验收项（编号）、依赖项是否就绪。验收判定标准在第二步查基线时确定。

## 第二步：查验收基线

动手前先读，不凭记忆：

1. 验收跟踪表（game：`03-acceptance.md` 的「验收跟踪」；software：PRD / DESIGN.md）——该验收项当前状态
2. 对应 Spec / DESIGN.md 的规则与实现决策
3. 验收判定标准（game：`03-acceptance.md` 的 `AC-*` 预期；software：论证文档的验证清单原文）

## 第三步：实现与测试

1. 实现遵循对应包 DESIGN.md（技术选型/架构已定）；实现级问题按第五步记录偏差
2. 测试纪律（见 `standards.md`）：隔离环境、不读真实配置、全绿才算过
3. 测试覆盖验收判定标准：先写能证明「验收项成立」的用例，再写边界

## 第四步：更新验收状态

1. 状态标记：◻ 未开始 / 🔄 进行中 / ✅ 通过 / ❌ 失败（附原因）
2. 更新位置：game 更新 `03-acceptance.md` 的「验收跟踪」；software 更新验收跟踪表 + 对应 DESIGN.md
3. 部分覆盖时标 🔄 并注明已覆盖/未覆盖部分

## 第五步：记录偏差（实现与设计冲突时）

四段式记录：

1. **现象**：实现时暴露的问题（可复现）
2. **判断**：违反哪条设计原则/验收项（如「违反 A5 一切可审计」）
3. **修复**：实际怎么改
4. **回写**：结论性偏差回写论证文档（带日期/版本锚点）；实现层细化不回写，留待评审

处理原则：能回写的回写论证文档（版本锚点记录），不能回写的留待评审；不擅自改设计结论。

## 第六步：汇报状态

输出：本次完成（验收项编号 + 状态）、测试结果、偏差记录（如有）、下一步（按依赖链的下一验收项）。

> **P0/P1 只表示验收优先级**；功能/包优先级用 `High / Medium / Low`。

## 交接

- 验收矩阵由 `game-docs` 创建；本 skill 只更新状态与偏差，不重写 `02` / `03`
- 连续执行到目标用 `execution-loop`；本 skill 负责状态与偏差
- 跨版本规划由 `roadmap-planning` 负责；本 skill 不排期
- 偏差若改变设计结论，回到 `game-docs/workflow.md` 的「变更与维护」流程，再回写

## 边界

- 不擅自扩大范围：验收项之外的功能改动先问用户
- 偏差记录是过程不是结论：结论性的设计问题回写论证文档，跟踪只留过程与状态
- 验证用的 key 与真实配置不入库、不落命令历史（与 `topic-research` / `code-digest` 同一纪律）
