# 实现跟踪（验收 + 偏差）

目标：每个验收项状态可查、每个实现偏差可追溯、设计文档与实现同步演进。

> 个人/团队偏好（验收表位置、状态标记、偏差格式）在 `standards.md`。

## 何时使用

- 开始实现一个验收项 / 完成一个验收项
- 实现中发现设计文档与实现冲突
- 汇报「做到哪了」「还剩什么」
- 版本收尾前核对验收清单

不适用：分期规划（用 `roadmap-planning`）、代码梳理（用 `code-digest`）、文档审核（用 `docs-audit`）。

## 操作顺序

1. 界定当前任务（对应哪个验收项）
2. 查验收基线
3. 实现与测试
4. 更新验收状态
5. 记录偏差（如有）
6. 汇报状态

## 第一步：界定当前任务

写下来：本次实现对应哪个验收项（编号）、依赖项是否就绪。验收判定标准在第二步查基线时确定。

## 第二步：查验收基线

动手前先读，不凭记忆：

1. 验收跟踪表（位置见 `standards.md`）——该验收项当前状态
2. 对应包 DESIGN.md 的验收状态与实现决策
3. 对应论证文档的验证清单原文（验收的判定标准）

## 第三步：实现与测试

1. 实现遵循对应包 DESIGN.md（技术选型/架构已定）；实现级问题按第五步记录偏差
2. 测试纪律（见 `standards.md`）：隔离环境、不读真实配置、全绿才算过
3. 测试覆盖验收判定标准：先写能证明「验收项成立」的用例，再写边界

## 第四步：更新验收状态

1. 状态标记：◻ 未开始 / 🔄 进行中 / ✅ 通过 / ❌ 失败（附原因）
2. 更新位置：验收跟踪表 + 对应包 DESIGN.md 的验收状态（就近工程，两处同步）
3. 部分覆盖时标 🔄 并注明已覆盖/未覆盖部分

## 第五步：记录偏差（实现与设计冲突时）

四段式记录：

1. **现象**：实现时暴露的问题（可复现）
2. **判断**：违反哪条设计原则/验收项（如「违反 A5 一切可审计」）
3. **修复**：实际怎么改
4. **回写**：结论性偏差回写论证文档（带日期/版本锚点）；实现层细化不回写，留待评审

处理原则：能回写的回写论证文档（版本锚点记录），不能回写的留待评审；不擅自改设计结论。

## 第六步：汇报状态

输出：本次完成（验收项编号 + 状态）、测试结果、偏差记录（如有）、下一步（按依赖链的下一验收项）。

## 边界

- 不擅自扩大范围：验收项之外的功能改动先问用户
- 偏差记录是过程不是结论：结论性的设计问题回写论证文档，跟踪只留过程与状态
- 验证用的 key 与真实配置不入库、不落命令历史（与 `topic-research` / `code-digest` 同一纪律）
