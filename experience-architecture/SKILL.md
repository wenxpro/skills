# 体验架构（Experience Architecture）

目标：在产品还小的时候，用一页图固定「产品有哪些表面、怎么走、状态归谁、什么被延后」，避免功能长出来后再补壳。

## 何时使用

- 产品有多个屏幕、模式或入口
- 即将新增第二个入口/模式/屏幕
- 需要设计首页、配置、暂停、结果、设置、重试等产品级流程
- 有持久设置、存档、元进度或平台壳层
- 返回/暂停/恢复行为开始出现歧义
- 需要判断「壳层现在做，还是延后」

不适用：

- 单屏工具，没有导航和产品级状态
- 纯视觉/品牌/组件规范（用设计系统）
- 代码模块/依赖边界（用 `responsibility-design`）
- 游戏内容、数值、关卡设计（用 `game-docs`）
- 只问某个页面的排版/交互细节

## 核心不变量

1. **一个根入口，最多两层导航。** 根 → 分类 → 详情；详情回分类，分类回根。
2. **产品状态与业务状态分离。** 屏幕/导航状态（AppState）不等于局内/会话状态（RunState / SessionState）。
3. **每个表面都有入口、退出、返回和 owner。** 不允许死链、不可返回、返回点不一致。
4. **每个模式都有完整闭环。** Setup → Run → Result → Retry/Exit，或等价流程。
5. **暂停作用域显式。** 写清暂停谁、不暂停谁；菜单不能被业务暂停冻结。
6. **延后项必须有触发器。** 为什么延后、什么条件触发、预估成本、谁负责。
7. **表面变更就是架构变更。** 新增屏幕/入口/持久状态时，先更新 Experience Map，再写代码。
8. **一页收敛。** 只画拓扑、状态、入口/出口、延后项；不画完整视觉稿。

## 工作流

1. **列表面**：屏幕、覆盖层、模式、入口、系统级页面。
2. **画拓扑**：根入口、两层导航、每个表面的边。
3. **定状态所有权**：产品状态 / 会话状态 / 局内状态 / 持久状态；谁创建、谁销毁、谁暂停、谁恢复。
4. **定生命周期**：创建、加载、激活、暂停、恢复、销毁；重开/返回时清什么。
5. **定输入与焦点**：Esc/Back、焦点顺序、鼠标/键盘/手柄；菜单和局内输入隔离。
6. **列延后项**：延后表面、原因、触发条件、成本、owner。
7. **评审**：新用户、回访用户、UX、技术、QA 各问一个问题。
8. **交接**：验收种子、实现包、文档位置。

## 触发门

出现以下任一情况，先更新 Experience Map，再进实现：

| 触发 | 必须先做什么 |
|---|---|
| 新增第二个入口/模式/屏幕 | 更新 Experience Map + 记录决策 |
| 新增持久设置/存档/元进度 | 定义状态所有者、清理策略、迁移方式 |
| 新增暂停/结算/重试路径 | 定义暂停作用域、返回点、状态重置 |
| 新增平台壳层 | 定义输入/焦点、生命周期、平台差异 |
| 返回行为出现歧义 | 停止实现，先定导航规则 |

## 输出要求

完成一次体验架构设计，至少交付：

1. 一页 Experience Map（模板见 `templates/experience-map.md`）
2. 导航与状态所有权决策（为什么一个根、为什么两层、谁拥有什么）
3. 延后项清单（原因、触发条件、成本、owner）
4. 验收种子（屏幕转换、返回、暂停、重试、清理）
5. 交接说明（文档位置、实现包、评审结论）

## 边界与反模式

- 不替代视觉设计、组件规范或代码架构。
- 不为未来所有屏幕做完整建模；只覆盖当前 + 下一步，其余进延后清单。
- 不把「功能列表」当「体验架构」；必须画边和状态。
- 不做深层菜单树；入口成本过高时先砍层级。
- 不静默延后壳层；延后必须留触发器。
- 不把单个局内界面当成产品全部表面。

## 交接

| Skill | 关系 |
|---|---|
| `game-docs` | 游戏内容、规则与验收；本 skill 定产品表面与流程 |
| `docs-core` | 文档槽位与单一事实源；Experience Map 作为入口/决策/验收附件 |
| `responsibility-design` | 代码模块与依赖；本 skill 定产品级状态所有权 |
| `review` | 体验架构评审；使用 `profiles/experience.md` |
| `execution-loop` | 按触发门拆实现包，不跳过壳层 |
| `implementation-track` | 屏幕/流程验收状态与偏差 |
| `docs-audit` | 文档漂移与交叉引用检查 |
