# 连续执行闭环

目标：用户只需要说一次「做到哪」，之后由 agent 连续推进到目标，而不是每完成一个小步骤就停下来问「继续吗」。

> 个人/团队偏好（批量大小、验证门、汇报格式）在 `standards.md`；执行约定模板在 `templates/execution-contract.md`。

## 何时使用

- 用户说「连续做」「做到 X 再汇报」「别每一步都问我」
- 一个目标可以拆成多个有依赖的工作包
- 需要边实现边测试、提交、更新文档/验收状态
- 需要把「计划」真正执行到可验收状态

不适用：

- 只需要一个方案或一次讨论，不需要落地
- 目标本身还没定，需要先做 roadmap-planning
- 当前里程碑的 Spec / 验收还没写，需要先走 game-docs / docs-core
- 单点问答、代码解释、一次性小修

## 核心规则

1. **只问一次目标。** 开工前确认：做到哪、DoD、约束、不能做什么、验证门。
2. **目标明确后不再逐项请示。** 按工作包连续执行，直到目标完成或触发止损。
3. **每个工作包必须闭环。** 实现 → 测试 → 修复 → 提交 → 更新追踪，再进入下一个。
4. **不允许把「计划完成」当「执行完成」。** 只有代码/文档/验证都到位才算完成。
5. **不允许隐藏失败。** 测试失败要么修，要么作为阻塞上报，不能跳过。
6. **提交粒度按工作包，不按文件。** 每个提交应可回滚、可验证。
7. **只在真实阻塞时停。** 见「止损条件」。

## 第一步：执行约定（只问一次）

如果用户已经给出目标，直接整理成执行约定，不再重复问。缺少关键项时才问一次。

执行约定至少包含：

| 项 | 内容 |
|---|---|
| 目标 | 这次连续执行到哪里 |
| DoD | 什么状态算完成 |
| 范围 | 明确要做 / 不做 |
| 验证门 | 测试、回归、性能、文档检查 |
| 提交策略 | 每个工作包提交，是否推送 |
| 人工步骤 | 试玩、评审、外部账号等 |
| 止损 | 哪些情况必须停下来问 |

写入 `templates/execution-contract.md` 或项目现有计划文档，之后按它执行。

## 第二步：拆工作包

把目标拆成有依赖顺序的工作包。每个工作包必须有：

- 唯一目标
- 依赖项
- 验收/测试方式
- 预计产出（文件、提交、文档）
- 是否可独立提交

工作包数量不要为了「看起来细」而膨胀；一个工作包应该能在一次连续执行中闭环。

## 第三步：连续执行循环

对每个工作包：

1. **确认基线**：读当前代码/文档/验收状态，不凭记忆。
2. **实现**：只改该工作包范围内的内容。
3. **自测**：跑相关测试/回归/检查；失败先修。涉及行为、数值/配置、状态重置、UI 数量或刷新等高风险改动时，按 `code-review` 的合并前检查选验证。
4. **更新文档/追踪**：状态、验收、ADR、计划表按项目规范更新。
5. **提交**：一个工作包一个逻辑提交；提交信息说明做了什么。
6. **进入下一个**：不询问「继续吗」。

循环直到：

- 目标完成
- 或触发止损条件

## 第四步：止损条件

只有以下情况停下来问用户：

- 目标/范围出现歧义，继续做会改变设计结论
- 需要删除/覆盖用户未提交的工作
- 需要不可逆操作（强制推送、删分支、删数据、发布）
- 缺少账号、密钥、网络、外部服务
- 测试连续失败，且修复需要改变设计
- 需要真人试玩、评审或主观判断
- 发现目标本身不成立，继续执行会浪费更多时间

停下来时，必须说明：卡在哪、已经做了什么、可选方案、建议。

## 第五步：交付汇报

目标完成后一次性汇报：

1. 完成了哪些工作包（编号 + 状态）
2. 测试/回归/性能证据
3. 文档/追踪更新位置
4. 偏差与未决问题
5. 提交列表与推送状态
6. 下一批建议（如果还有）

不要用「已完成」代替证据；每条结论要能指向测试、日志、文件或提交。

## 进度与反模式

进度表与反模式清单见 `standards.md`；部分完成必须标 `🔄` 并写清已覆盖/未覆盖。

## 交接

- 交付阶段：由 `delivery-stage` 组织
- 目标/分期：`roadmap-planning`
- 验收状态/偏差：`implementation-track`
- 规则文档与 Spec：`docs-core` / `game-docs`
- 架构边界：`responsibility-design`
- 代码审查 / 合并前检查：`code-review`
- 提交：`git-commit`
- 收尾评审：`review`

## 边界

- 本 skill 不是「无限自主」：不可逆操作、范围变化、人工验证必须停。
- 不擅自扩大目标；发现额外问题先记录，不顺手改。
- 不替代项目验收标准；只负责执行到标准。
