# 连续执行规范（个人/团队风格标准）

本文件包含执行闭环的默认偏好，可整体替换。

## 批量大小

- 一个工作包 = 一次可独立验证的交付。
- 一个工作包内不询问「继续吗」。
- 工作包之间可以连续执行；只有触发止损才停。
- 单个工作包如果超过一天仍未闭环，拆小，不要硬撑。

## 验证门

每个工作包至少过一道：

- 代码：相关单元/结构测试
- 行为：回归或验收用例
- 文档：文档检查（如 `check-docs`）
- 性能：涉及性能敏感路径时跑性能基线（示例：渲染密度、生成量等）
- UI：至少人工观察或截图检查（如项目支持）
- 高风险改动：按 `code-review` 的合并前检查补配置校验、重开一致性、UI 数量/刷新等结果

全绿才提交；部分通过标 `🔄`，不能标 `✅`。

## 提交策略

- 一个工作包一个逻辑提交。
- 提交信息按项目规范（默认 Conventional Commits）。
- 不提交半成品、临时调试代码、未通过的测试。
- 需要推送时按项目远程配置推送；推送失败作为阻塞上报，不反复重试超过 3 次。

## 进度表

默认使用：

| ID | 工作包 | 状态 | 证据 |
|---|---|---|---|
| W1 |  | ◻/🔄/✅/❌ | 测试/提交/文件 |

状态语义：`◻ 未开始 / 🔄 进行中 / ✅ 通过 / ❌ 失败（附原因）`。

## 进度追踪规则

- 有 `implementation-track`：用它更新 `AC-*` 状态与偏差。
- 有项目计划表：更新计划表的 `◻ / 🔄 / ✅ / ❌`。
- 都没有：在回复中维护一个简单进度表，并在目标完成时汇总。
- 部分完成必须标 `🔄`，并写清已覆盖/未覆盖。

## 汇报格式

目标完成时：

```text
完成：W1 / W2 / W3
证据：测试 X 通过；回归 seed1/2；性能 <指标> 达标
文档：<规则> / <验收> / ADR 已更新
提交：abc1234、def5678
偏差：无 / 见下
剩余：无 / 下一批建议
```

## 止损阈值

- 同一测试连续失败 3 次且原因不明 → 停
- 需要改设计结论 → 停
- 需要不可逆操作 → 停
- 需要外部账号/网络/真人 → 停
- 目标范围明显扩大 → 停，重新确认

## 与其它 skill 的配合

- 先 `roadmap-planning` 定目标，再 `execution-loop` 连续执行。
- 执行中状态写 `implementation-track`。
- 架构边界先走 `responsibility-design`。
- 提交用 `git-commit`。
- 收尾用 `review`。

## 反模式

- 每完成一个文件就问「继续吗」
- 只输出计划，不执行
- 目标没定义就开始写代码
- 测试失败后跳过或静默删除测试
- 把多个不相关工作包塞进一个提交
- 为了「看起来完成」而改验收标准
- 遇到真实设计冲突仍硬推
