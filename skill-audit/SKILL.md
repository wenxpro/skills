# Skill 仓库审核

目标：每个 skill 的通用层只放「换一个项目仍成立」的内容；项目/领域细节下沉到 profile 或标注示例；结构可安装、触发不混淆。

## 何时使用

- 新增或修改 skill 后
- 仓库发布前
- 怀疑通用层混入项目细节（具体数值、文件格式、项目名、编号）

不适用：项目文档集审核（用 `docs-audit`）、skill 内容的多角色评审（用 `review` + docs profile）。

## Skill 设计模型（审计判据来源）

- **职责**：一个 skill 一类任务；`description` 写清做了什么、何时用、何时不用
- **触发边界**：负面清单与正面清单同等重要
- **执行边界**：边界 / Guardrails、反模式、止损条件
- **交接边界**：与相邻 skill 的分工与输入输出，依赖方向明确
- **分层**：通用流程 / 可替换偏好 / 示例 / 模板（见第二步判据）
- **反模式**：description 过宽、无边界节、skill 间循环依赖、把偏好写进通用层

## 操作顺序

1. 结构扫描
2. 抽象分层扫描
3. 术语一致性
4. 交叉引用与职责边界
5. 输出报告

## 第一步：结构扫描

逐个 skill 检查：

- 目录名 = frontmatter `name`（小写字母数字、单连字符）
- `description` 写清触发场景与「不适用」，长度 ≤1024
- 引用的文件都存在（`standards.md`、`templates/...`、`scripts/...`）
- `standards.md` 可整体替换：通用流程不依赖其具体条款
- 无本机绝对路径；示例用 `<target>`、`<project>`

改过 `description` 后，按 `references/trigger-cases.md` 跑触发回归。

## 第二步：抽象分层扫描（核心）

按三层判据判定每段内容：

| 层 | 可以写 | 不要写 |
|---|---|---|
| 通用规则 / 流程（`SKILL.md`） | 领域无关的规则、检查项、决策问题 | 项目名、版本号、具体功能名、数值阈值、文件格式、专属工具名 |
| 领域 profile（`standards.md` 的 profile 节） | 游戏/软件等领域概念与角色 | 本项目专有名词、本项目数值 |
| 示例（明确标注「示例」） | 具体实现片段、领域例子 | 把示例当成规范规则 |
| 模板（`templates/`） | 领域词（模板是脚手架，不是规则） | 项目实际内容 |

判据：**换一个项目，这句话还成立吗？** 不成立就下沉到 profile 或标注示例。

扫描种子（grep）：

- 具体数值与阈值：`\d+\s*(FPS|ms|秒|分钟|人|%)`
- 本机路径与环境（扫描模式）：`~/`、`/Volumes/`、用户目录
- 文件格式与引擎概念：`.tres`、`.tscn`、Godot / Unity / Unreal
- 项目专有名词：具体包名、孤立编号（如 `09`）、功能名（HUD、升级表、奖励发放）
- 专属工具名：`check-docs`、`check-review`（保留时加「如」或移到 standards）
- 示例编号：`A1/A5`、`M1-M20`（应标注为示例或移到 profile）

判定后给下沉建议：移到 `standards.md` 的 profile 节，或加「示例」标注。**优先下沉而不是删除**——项目细节是资产，放对层即可。

## 第三步：术语一致性

1. **以术语表为准**：本仓库的规范说法与废弃词见 `references/terminology.md`；skill 引用的项目专有术语，以项目术语表为准。
2. **全库扫描**：`SKILL.md`、`standards.md`、`README.md`、`templates/` 都要扫，不只改入口文件。
3. **允许引用旧词**：术语表的「不要写」列、明确标注的迁移说明、历史原文可以保留；其他命中一律替换。
4. **同一概念只用一种说法**：不要在同一段混用规范词和旧词。
5. **跑检查**：替换后跑 `scripts/check-skills.sh`；它包含废弃词扫描，零命中才算完成。

## 第四步：交叉引用与职责边界

- 各 skill 的「不适用」「交接」指向的 skill 都存在
- 同一检查项不在多个 skill 重复维护（重复时确认是引用关系）
- 职责边界：两个 skill 的对象/触发是否冲突（如文档审核 vs 仓库审核；代码过时 vs 文档漂移）
- 阶段 playbook skill（如 `design-stage`）只写本阶段入口、检查、出口与交接；不复制生命周期表或具体方法，避免和底层 skill 双重维护
- 关系图与交接文字一致（如 roadmap 的下一步是否在两边都写了 execution-loop）

## 第五步：输出报告

沿用 `docs-audit` 的三组格式：

- **必须改**：违反抽象分层、引用断裂、frontmatter/目录不匹配、废弃术语未替换
- **建议改**：示例标注缺失、领域词未下沉、职责边界模糊
- **核对无误**：列出核对的 skill 与检查项

## 反例库（本仓库已实际发现）

- 通用 `SKILL.md` 写「HP/冷却」「`.tres` 存状态」「HUD 判断升级 ID」——游戏与 Godot 专有内容进了通用层
- 示例写「文档：09 / 03」——`09` 不在本仓库 00~07 编号体系内，示例自身不自洽
- 验证门写「涉及密度/渲染/生成」——领域词未标注示例
- 检查项写「模式/难度相关数值」——领域概念混入通用审核清单
- 统一术语后只改 `SKILL.md`，README/模板仍留旧词——按 `references/terminology.md` 全库扫描，并跑 `scripts/check-skills.sh`

这些模式应作为 grep 种子，每次扫描。

## 边界

- 只审 skill 仓库；项目文档集审核用 `docs-audit`
- 报告先于修改：先输出三组清单，确认后再动文件
- 不改变 skill 设计意图；修复优先下沉，不删除项目细节
- 判据以本 skill 为准，README 只引用

## 与 README 的关系

三层判据以本 skill 为准；README「新增/维护 skill」只保留一句「抽象边界见 `skill-audit`」，避免两处维护。
