# 设计阶段

目标：把“要做什么”收敛成可评审、可排期、可验收的设计结论。

> 图设计按风险选最小图集，详见 `references/diagram-playbook.md`；填写模板见 `templates/design-diagrams.md`。决策锁、Pre-mortem 与 Kill Criteria 见 `references/decision-locks.md`。

## 入口

从零设计、架构调整、反馈回流后的重新设计，都从这里进入。

开始前确认：

1. 设计问题、范围与明确不做的事
2. 约束、决策人与时间盒
3. 需要的输入已列，不凭记忆设计
4. 评审方式与参与角色已定

不适用：代码实现 → `delivery-stage`；代码审查 → `code-review`；验收状态 → `implementation-track`；单点方法问答 → 对应专业 skill。

## 输入

| 输入 | 什么时候需要 | Skill |
|---|---|---|
| 外部生态、竞品、技术选型 | 方案依赖外部事实 | `topic-research` |
| 现有代码、架构、演进 | 设计基于现状或要做重构 | `code-digest` |
| 文档健康度 | 设计文档可能过时、矛盾、重复 | `docs-audit` |
| 当前验收状态与偏差 | 设计接在已有实现之后 | `implementation-track` |

只读与当前设计问题相关的部分；外部事实与代码事实分开标注，推断显式写“未验证”。

## 轨道

| 轨道 | 产出 | Skill |
|---|---|---|
| 体验架构 | 产品表面、导航、状态所有权、生命周期 | `experience-architecture` |
| 职责设计 | 上下文、模块所有权、依赖方向、接口、状态边界 | `responsibility-design` |
| 文档规则 | 行为规则、验收、ADR、文档槽位 | `game-docs` / `docs-core` |

规则：

- 新系统先定体验架构，再把产品状态边界落到代码模块边界；已有系统可并行，但交接不能省。
- 设计阶段就要定模块边界与依赖方向，不留到实现后修补。
- 小问题不必三轨全开，只开相关轨道；跨模块、跨表面、持久状态变化必须收敛。

## 图设计

图不是全套 UML，也不是“画得越多越设计”。按风险选最小图集，一张图只回答一个问题。

| 图 | 回答 | 什么时候必须 |
|---|---|---|
| 上下文/组件图 | 边界、所有权、静态依赖 | 新模块、新上下文、依赖方向变化 |
| 生命周期状态图 | 动态对象从创建到清理有哪些状态和转换 | 新增有状态对象、异步/池化/重试 |
| 时序图 | 一次流程的参与者、调用、事件顺序 | 多条创建路径、跨上下文事件、失败/清理路径 |
| 所有权/生命周期表 | 谁创建、谁注册、谁结束、谁清理、作用域 | 所有动态对象 |
| 事件/信号表 | 谁发、谁听、顺序、幂等 | 跨上下文事件 |
| 类图/接口图 | 类型、接口、静态依赖 | 新抽象、新接口、继承关系 |

规则：

- **静态结构用上下文/类图；动态行为用状态图/时序图。** 类图不能证明运行时接线。
- 动态对象至少写清：创建入口、注册方式、结束条件、清理方式、作用域。
- 有多条创建路径（正常创建、派生创建、事件触发、测试）时，每条路径都要有时序图或等价文字。
- 图必须指向代码位置、测试或决策记录；画完不落地等于没画。
- 低风险改动可以只画上下文 + 一张主路径时序；高风险生命周期变更必须补状态图、所有权表和事件表。

## 设计检查

提交评审前逐项确认：

- 新表面有入口、退出、返回；延后项有触发器
- 状态有唯一所有者，产品状态与业务状态分离
- 模块依赖方向明确，无双向依赖
- 动态对象有创建、注册、结束、清理路径；不是“创建后就假设会自动接上”
- 多条创建路径都有时序图或等价文字；跨上下文事件有发出者/监听者/顺序
- 图与规则、验收、测试能互相对应；没有只画不用的图
- 行为规则可判定，验收种子能转成验收项
- 不可逆决定已标为单向门；有最小验证、回滚条件或评审结论
- 已做 Pre-mortem；Kill Criteria 可观察、有 owner/时间盒
- 未决项有 owner 与下一步

## 收敛与出口

按“界定问题 → 补输入 → 选轨道 → 标未决项 → 评审”收敛，至少留下：

1. 设计问题、范围、约束
2. 采用的事实与输入
3. 体验架构 / 职责设计 / 文档规则 / 最小图集的实际产物
4. 关键决策与未决问题
5. 验收种子与实现工作包
6. 评审结论或待评审项

方向、范围、架构、体验变化必须过 `review`；通过后交 `roadmap-planning` 排期，再进 `delivery-stage`。

## 反模式

- 用功能列表代替设计：没有边界、状态、依赖和取舍。
- 只画类图或上下文地图，不画生命周期状态和时序；静态结构看起来完整，运行时接线仍然缺失。
- 图只画正常路径，不画失败、回收、超时、重开和清理路径。
- 跳过职责设计直接实现，或把模块边界留到重构。
- 用实现验证代替设计评审。
- 把调研/代码梳理的事实直接当设计结论，事实与判断不分。
- 把单向门当双向门：未验证就铺内容/美术/经济。
- 只写“后续优化”，没有 Kill Criteria、owner 和时间盒。
- 在设计阶段改代码。

## 交接

- 上一阶段：`feedback-stage`（重新设计）或无
- 下一阶段：`delivery-stage`；排期 `roadmap-planning`
- 评审：`review`
- 会话切换/交接：`session-handoff`
