# 演进规划规范（个人/团队风格标准）

本文件包含两个 profile。按项目文档结构选择，不要混用：`docs/00-README.md` + 00~05、07 用 Game profile；PRD + 各包 DESIGN.md 用 Software profile。

## Software profile

以下为默认偏好，其他团队可整体替换。

### 分期定义

- **MVP**：验证内核（产品需求文档对应章节，验收编号如 M1-M20）
- **V1**：产品化（PRD 4.2：TUI 完整、扩展系统、RPC、认证子系统）
- **V2**：订阅化（PRD 4.3：云端会话同步、团队共享执行环境、统一策略）
- **功能/包优先级 `High / Medium / Low`**：标注在各包 DESIGN.md，属包级排序，与 MVP/V1/V2 里程碑分期并存
- **P0/P1 只用于验收优先级**（定义见 `docs-core`），不用于包级排序，避免同名不同义

### 验收项来源

- 八篇论证文档（内核闭环、上下文装配、模型与认证、扩展生态、多形态前端、会话数据与遥测、多Agent编排、评测体系）末尾的验证清单，共 71 条，可按里程碑拆解
- 设计总纲第五部分的自检项
- 归组后形成编号验收（如 M1-M20），定义在 PRD 的验收章节

### 落点约定

- 生态/竞品观察的落点 → 设计总纲 1.5 观察条目（不另立文档）
- 机制方向落点 → 对应论证文档（如「上下文装配 V1 方向」）
- 包内能力 → 包 DESIGN.md
- 规划结论 → PRD 第四/六节与 README「下一步」

### 排序依据

- 依赖链是硬约束：被依赖项先实现（示例：Esc 中断 → abort 协议 → 触发式规则注入）
- 同级内排序：体验落差 > 机制层先于策略层
- 订阅项必须满足「本地给不了」条件（付费墙规则：云端同步、团队共享执行环境、统一策略——本地能做的功能不进订阅范围）

## Game profile

适用于 `game-docs` 的 `00~05、07` 文档结构（`06` 可选）。

### 输入

- `01-run-brief.md`：单局目标、范围、止损条件、后置内容
- `02-design-spec.md`：行为规则、开放问题
- `03-acceptance.md`：`AC-*` 用例、P0/P1、验收跟踪、偏差记录
- `05-reviews/`：评审组条件、行动项与试玩结论

### 分期定义

- **M0 立项**：01 / 02 / 03 / ADR / 评审完成
- **M1 灰盒**：可玩循环 + P0 验收 + 5 人试玩
- **M2 垂直切片**：内容、UI、音效、外部试玩
- **MVP**：M1 通过后的最小可发布版本
- **V1**：角色 / 内容 / 平台扩展
- **V2**：长线 / 联机 / 商业化（如适用）

### 验收项来源

- `03-acceptance.md` 的 `AC-<类别>-<序号>`
- `02-design-spec.md` 的 P0/P1 规则
- `05-reviews/` 的条件与试玩止损结论

### 落点约定

- 当前行为 → `02-design-spec.md`
- 当前验收 → `03-acceptance.md`
- 跨版本计划 → 规划文档 / `00-README.md` 的「下一步」
- 未决问题 → `02-design-spec.md` 的「开放问题」

### 排序依据

- 依赖链优先：被依赖的机制先排
- **P0 验收优先**，P1 可后置
- 体验落差 > 内容量
- 无法写成 `AC-*` 的项，不排入当前里程碑

### 优先级命名

语义见 `docs-core`。

- 验收：`P0` / `P1`
- 功能 / 包：`High` / `Medium` / `Low`

> P0/P1 只表示验收优先级，不要拿来排功能优先级。
