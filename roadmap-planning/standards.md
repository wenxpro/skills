# 演进规划规范（个人/团队风格标准）

本文件包含两个 profile。按项目文档结构选择，不要混用：`docs/00-README.md` + 00~05、07 用 Game profile；PRD + 设计文档（可选包级 `DESIGN.md`）用 Software profile。

## Software profile

以下为默认偏好，其他团队可整体替换。**范围与分期内容不在本文件写死**：以各项目 PRD 为准，本文件只定结构与来源。

### 分期结构

- **MVP**：验证内核的最小闭环（对应 PRD 的 MVP 章节与验收章节）
- **V1**：产品化或自用增强（对应 PRD 的 V1 章节）
- **V2**：更远期，或整体推迟（对应 PRD 的 V2 章节）
- **功能/包优先级 `High / Medium / Low`**：标注在包级设计文档（若有），属包级排序，与 MVP/V1/V2 分期并存
- **优先级**：验收用 P0/P1，功能/包用 `High / Medium / Low`，语义见 `docs-core`，两套不混用
- 分期名称与数量可裁剪；裁剪后仍按「MVP → V1 → V2」的依赖顺序表达

### 验收项来源

- 各设计文档末尾的验证清单（条数随文档集，规划时现数，不引用硬编码总数）
- 验收槽位（定义见 `docs-core`）的 `AC-*` 矩阵
- 里程碑门（如 `M1`、`P0 组`）只作聚合视图，必须能展开到 `AC-*`（规则见 `docs-core`）；不要假定某个项目一定用某套编号

### 落点约定

- 生态/竞品观察的落点 → 项目总纲的观察条目（不另立文档）
- 机制方向落点 → 对应设计文档（如「上下文装配 V1 方向」）
- 包内能力 → 包级设计文档（若有）
- 规划结论 → PRD 的范围/验收章节与 README「下一步」

### 排序依据

- 依赖链是硬约束：被依赖项先实现
- 同级内排序：体验落差 > 机制层先于策略层
- 商业化项必须满足「本地给不了」条件（付费墙规则属项目决策，按项目总纲结论执行）

## Game profile

适用于 `game-docs` 的 `00~05、07` 文档结构（`06` 可选）。

### 输入

- `01-run-brief.md`：单局目标、范围、止损条件、后置内容
- `02-design-spec.md`：行为规则、开放问题
- `03-acceptance.md`：`AC-*` 用例、P0/P1、验收跟踪、偏差记录
- `05-reviews/`：评审组条件、行动项与试玩结论

### 分期定义

- **M0 立项**：01 / 02 / 03 / ADR / 评审完成
- **M1 灰盒**：可玩循环 + P0 验收 + 5 人试玩
- **M2 垂直切片**：内容、UI、音效、外部试玩
- **MVP**：M1 通过后的最小可发布版本
- **V1**：角色 / 内容 / 平台扩展
- **V2**：长线 / 联机 / 商业化（如适用）

### 验收项来源

- `03-acceptance.md` 的 `AC-<类别>-<序号>`
- `02-design-spec.md` 的 P0/P1 规则
- `05-reviews/` 的条件与试玩止损结论

### 落点约定

- 当前行为 → `02-design-spec.md`
- 当前验收 → `03-acceptance.md`
- 跨版本计划 → 规划文档 / `00-README.md` 的「下一步」
- 未决问题 → `02-design-spec.md` 的「开放问题」

### 排序依据

- 依赖链优先：被依赖的机制先排
- **P0 验收优先**，P1 可后置
- 体验落差 > 内容量
- 无法写成 `AC-*` 的项，不排入当前里程碑

### 优先级命名

语义见 `docs-core`。

- 验收：`P0` / `P1`
- 功能 / 包：`High` / `Medium` / `Low`

> 优先级语义见 `docs-core`。
