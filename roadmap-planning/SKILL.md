# 演进规划

目标：让「下一步做什么」由文档推导出来，不凭感觉。规划的输入是设计文档里已写下的结论（验证清单、观察落点、开放问题），规划的输出是分期表与下一步。

> 个人/团队偏好（分期定义、验收项来源、落点约定）在 `standards.md`。

## 文档 profile

先判断项目使用哪套文档，不要混用：

| 文档结构 | profile | 读 `standards.md` 的 |
|---|---|---|
| `docs/00-README.md` + 00~05、07 | **game** | 「Game profile」 |
| PRD + 各包 `DESIGN.md` | **software** | 「Software profile」 |
| 不确定 | — | 先问用户，不要猜 |

本 skill 只读设计结论，不重写 Spec / Acceptance。

## 何时使用

- 「接下来做什么」「V1/V2 范围是什么」
- 新想法/新结论排期（进哪一期、什么优先级）
- 里程碑拆解（验证清单按阶段归组）
- 观察条目的「落点」汇总成计划

不适用：当前里程碑内的 Spec / 验收（用 `game-docs`）、单个任务实现中的验收与偏差记录（用 `implementation-track`）、文档集审核（用 `docs-audit`）。

## 里程碑与工作包两层

规划里同时存在 `M`（里程碑/验收门）和 `W`（工作包/依赖顺序），它们是两层，不是两套并行计划：

- **M 回答“什么算完成”**：以验收项为出口，不以“W 看起来都做完了”为出口。
- **W 回答“先做什么”**：按依赖链排序，一个 W 只挂一个主 M。
- **跨 M 只写 `W → W` 依赖**，不把同一任务抄进两个 M；一个 W 同时服务两个 M 时，先拆 W。
- **持续工作**（文档、决策、维护）不占某个单一 M 的出口门。
- 输出一张映射表：`M | 主要 W | 出口条件`，并在依赖图里保留 W 的顺序。

反模式：用 W 编号当版本号；M 里重复列 W 的任务；把“计划完成”当成“验收完成”。

## 操作顺序

1. 界定规划问题
2. 收集规划素材
3. 归位与排序
4. 标落点
5. 输出规划结论

## 第一步：界定规划问题

写下来：规划什么（整个路线图 / 下一期 / 单个新想法）、约束（当前阶段、人力、时间盒）、结论写进哪里。

## 第二步：收集规划素材

从文档收集，不凭记忆：

1. 当前阶段与验收状态（入口见 `standards.md`）
2. 分期定义与各期范围（`standards.md` 的分期表）
3. 验证清单（各论证文档末尾，验收标准的来源）
4. 观察/结论里已写明的「落点」（如「可进 V1 的权限钩子示例集」）
5. 开放问题与预测（标注验证状态 = 预测的项，规划时保持标注）
6. 功能/包优先级（`High / Medium / Low`；P0/P1 只用于验收优先级，定义见 `standards.md`）

## 第三步：归位与排序

新想法/待办按以下规则归位：

1. **依赖链先行（硬约束）**：被依赖的机制必须先排——依赖链决定「能不能排、先排谁」，同级内才用下面的规则排序
2. **付费墙规则**：本地能做的功能不进订阅范围，订阅只排本地给不了的事（本项目例见 `standards.md`）
3. **机制层先于策略层**：内核机制（能力）先于产品壳策略（配置/默认值）
4. **体验落差排序**：交互/表达类按「当前体验落差大小」排，最难受的先做
5. **验证闭环**：排入的每项有验收方式（验证清单条目或自检项），无法验收的不排入

## 第四步：标落点

每项计划标注落点（结论写进哪个文档），规则见 `standards.md` 的落点约定。规划本身不新增文档，只更新既有文档的对应章节。

## 第五步：输出规划结论

1. **M/W 映射表**：M、主要 W、出口条件
2. **分期表**：阶段、范围、验收项（编号）、状态
3. **下一步**：当前阶段的具体下一项（按依赖链），附理由
4. **待决问题**：排不进当前分期或需要设计讨论的项

输出先给用户确认，再写入文档。写完后回读一遍，确认与既有编号（验收项、决策编号）不冲突。

## 交接

- 输入：`game-docs` 的 `01 / 02 / 03 / 05 / 06`，或软件 profile 的 PRD / DESIGN.md / 验证清单
- 输出：分期表、下一步、待决问题；**不改** `02` 的行为规则，也**不改** `03` 的验收判定
- 执行交给 `execution-loop` 连续推进；验收状态由 `implementation-track` 记录

## 边界

- 规划不改变设计结论；新结论先走设计流程（`topic-research` / 文档论证），再进规划
- 分期调整（如把 V2 项提到 V1）必须给理由并更新相关文档
- 预测项在规划中保持「预测」标注，不因排期而升级为事实
