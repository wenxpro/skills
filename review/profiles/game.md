# Profile — Game

## 角色

| 角色 | 关注点 | 否决权 |
|---|---|---|
| 目标玩家 | 易懂、想再来一局、反馈是否成立 | 体验不成立 |
| 游戏设计师 | 循环、选择、节奏、构筑 | 核心玩法不成立 |
| 技术负责人 | 可行性、性能、维护 | 技术不可行 |
| 美术 / UX | 可读性、表现成本、信息层级 | 画面不可读 |
| 制作人 | 范围、时间、砍线 | 超范围 |
| QA | 可测试性、边界、回归 | 验收不足 |

## 必问

1. 玩家在开场短时间内知道要做什么吗？
2. 这一局和上一局有什么不同？
3. 一局结束后是否愿意重开？
4. 哪个内容/机制最难解释？
5. 峰值同屏/压力场景下是否可读、可跑？
6. P0 规则是否都有验收？
7. 单局胜负与收尾是否明确？有没有“时间到就结束”的假高潮？
8. 前 1/3 是否出现承诺型选择，而不是只有数值？
9. 威胁成长是否跟得上玩家成长？防御堆叠有没有爆发检查？
10. 地图形态（固定/滚动/房间）是否与胜利条件、刷怪、节奏匹配？
11. 变换/进化是否定义继承、折算、失效，并向玩家披露？
12. 证据走到哪一层？静态预览、模拟、bot、真人，是否用低层证据替代高层结论？
13. 失败是否可归因？有没有压力来源、失败时间、构筑记录？

## 证据

- Run Brief
- Design Spec
- Acceptance
- ADR
- 试玩记录
- 性能 / 回归 JSON

## 文档

游戏文档本身由 `game-docs` skill 维护；本 profile 只负责角色与否决规则。
