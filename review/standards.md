# Review 标准与偏好

> 这是个人/团队偏好文件。其他团队可以整体替换，不需要改 `SKILL.md`。

## 结论

状态语义见 `docs-core`。只允许：

- `通过`
- `有条件通过`
- `否决`
- `Superseded`（评审结论仍有效，但方案被后续决策取代）
- `Archived`（仅归档，不参与当前决策）

`待定` 只能出现在草稿，不能进入 active 索引。

## 角色

- 角色由 profile 定义，不写死在流程里。
- 每个角色必须给出：认可 / 条件 / 否决理由。
- 每个角色有一票，但否决必须有可验证理由。
- 技术负责人可以因不可行/不可维护否决。
- QA 可以因不可验收/证据不足否决。
- 制作人/PM 可以因范围/时间否决。

## 记录

- 1~2 页。
- 必含：编号、日期、对象、结论、角色意见、条件与行动项、证据。
- 角色意见用表格，不写长篇「认可/条件」段落。
- 行动项格式：

```text
ID | 条件/行动 | 负责人 | 写入位置 | 截止
```

- 没有负责人或截止的行动项不算行动项。
- 评审记录只写**当前决策**；被否决/被取代的方案放「备选与否决理由」一节，最多 5 条。

## Active / Archive

> game profile 的目录结构如下；software / narrative 等其他 profile 按项目约定放置。

```text
05-reviews/
├─ README.md          # active + archive 索引
├─ 0001-...md         # active
└─ archive/
   └─ 0001-...md      # superseded / archived
```

- active 只保留仍影响当前版本的评审。
- 被取代的评审移到 `archive/`，顶部标 `Superseded`，并链接替代 ADR。
- 归档记录可以压缩成 1 页摘要；原文留在 git 历史。
- 没有关闭条件的评审不能进入下一阶段。

## 证据

| 评审类型 | 最少证据 |
|---|---|
| 游戏设计 | Run Brief、Design Spec、Acceptance、ADR、试玩记录 |
| 软件方案 | PRD/RFC、接口/数据说明、测试计划、监控/回滚 |
| 文档 | 文档集、链接、示例、自检结果 |
| 架构 | ADR、图、SLO、威胁模型、上线方案 |
| 体验架构 | Experience Map、状态所有权、延后项、关键流程验收 |

## 评审节奏

- 每个里程碑至少一次。
- 方向/架构变化：新 ADR + 评审。
- 纯数值/文案调整：不需要评审，走 Spec/Acceptance/Changelog。
- 评审后 24 小时内更新 active 索引。

## 跨 skill 约定

| 约定 | 规则 |
|---|---|
| 结论状态 | 通过 / 有条件通过 / 否决 / Superseded / Archived |
| 角色 | 由 profile 定义 |
| 行动项 | ID + 负责人 + 写入位置 + 截止 |
| 单一事实源 | 决策在评审记录 + ADR；行为在 Spec；验收在 Acceptance |
| 归档 | 不删除历史，移入 `archive/` |
