# 职责驱动设计规范（个人/团队风格标准）

本文件是可替换的默认偏好，说明上下文命名、依赖规则与违规分级。

## 上下文命名

示例：核心流程、领域能力、内容管理、表现层；换成其他领域时按业务职责命名。

- 用业务/职责命名，不用技术层命名。
- 差：`models`、`services`、`utils`、`helpers`、`common`

## 默认依赖方向

```text
Presentation
    │ 只读 ViewModel / 发输入
    ▼
Application（组合根、用例编排、Director）
    │ 调用领域规则
    ▼
Domain（实体、值对象、领域服务）
    │ 只依赖共享值对象/内容定义
    ▼
Shared（只读数据结构、内容定义）
```

- Infrastructure（配置、存储、网络、RNG）由 Application 使用；Domain 不直接依赖。
- 跨上下文不直接改内部字段；用方法、信号、端口或只读数据。
- 共享内核保持最小；不要把什么都塞进 `shared`。

## 动态对象与生命周期

- 每个动态对象只有一个权威创建入口；派生生成、事件生成、测试替身都不能各自直接实例化。
- 创建和注册是一个动作还是两个动作，必须写清；不能假设“创建后自然会被发现”。
- 生命周期的结束条件要区分正常结束、回收、超时、场景切换、重载。
- 副作用、统计、表现层提示的归属要在上下文地图里写清，不能由实体自己决定。
- 静态上下文地图不足时，配状态图和时序图；图清单按项目设计流程维护。

## 违规分级

| 级别 | 判定 | 处理 |
|---|---|---|
| High | 双向依赖、组合根承担规则、实体依赖内容目录 | 本迭代修 |
| Medium | 表现层知道领域 ID、跨上下文直接改字段 | 下个功能前修 |
| Low | 命名/目录不清晰、单次只读跨层 | 有空再修 |

## 第一个修正的选择

优先选：

1. 能独立测试
2. 能减少下一个功能的阻力
3. 不需要同时改 5 个以上文件
4. 不改变外部行为

如果修正会改变行为，先走项目规则/验收流程。

## ADR 触发条件

以下情况写 ADR：

- 新增/合并上下文
- 改变依赖方向
- 引入端口/适配器/事件
- 新增动态对象的统一创建入口或生命周期 owner
- 决定不上完整 DDD 或放弃某层
- 边界修正影响现有模块职责

只改目录/命名、不改职责的，不写 ADR。

## 行为保持重构门槛

- [ ] 有重构前基线：测试、固定种子/黄金输出、性能、关键指标
- [ ] 第一刀是低风险、可独立测试的
- [ ] 保留旧入口包装，调用方逐步迁移
- [ ] 每刀单独提交，可回滚
- [ ] 每刀后全量测试 + 基线回归一致
- [ ] 行为变化走规则/验收/ADR，不混在重构里

## 术语规范

重构相关表述只用标准术语，不生造比喻（如「减脂」「瘦身」）。

| 概念 | 标准术语 | 不要写成 |
|---|---|---|
| 应用启动时的依赖装配入口 | Composition Root（组合根） | 主函数、入口类 |
| 从类/模块中提炼职责 | Extract Class / Extract Function | 拆分、剥离 |
| 把函数移到合适模块 | Move Function | 搬代码 |
| 旧入口转发到新模块 | Delegation / Facade | 保留旧接口 |
| 不改变外部行为的重构 | Behavior-Preserving Refactoring | 纯重构 |
| 改变行为的重写 | Rewrite（不是重构） | 重构（误用） |

判据：重构 = 不改变外部行为；改变行为的是 Rewrite 或行为变更，走规则/验收/ADR。

## 与执行闭环配合

- 边界方案先写成上下文地图 + 违规表。
- 第一个修正写成工作包，交 `execution-loop`。
- 每个工作包结束更新 `implementation-track` 状态。
- 不把「画完上下文图」当完成；至少落地一条修正。
