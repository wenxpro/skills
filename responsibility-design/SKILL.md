# 职责驱动设计

目标：让「谁拥有什么、谁可以依赖谁、先修哪条边界」从口头约定变成可检查的上下文地图。

> 个人/团队偏好（上下文命名、依赖规则、违规分级）在 `standards.md`；上下文地图模板在 `templates/context-map.md`。

## 何时使用

- 设计阶段：新模块/新系统/新平台/新存储，先定上下文、所有权、依赖方向与接口
- 项目能跑，但模块边界靠感觉，`main`/`core` 越来越大
- 现有代码出现边界违规、双向依赖、组合根膨胀
- 想把一个项目里的架构经验抽象成团队规范
- 需要判断「要不要上 DDD / 六边形 / 模块化」

不适用：

- 当前里程碑的行为规则与验收（用 `game-docs` / `docs-core`）
- 单个任务的实现进度与偏差（用 `implementation-track`）
- 文档集交叉引用审核（用 `docs-audit`）
- 纯代码梳理/时间线（用 `code-digest`）

## 核心原则

1. **一个事实一个所有者。** 同一规则不能在两处维护。
2. **依赖方向固定。** Presentation → Application → Domain → Shared；基础设施被 Application 使用，不反向依赖 UI。
3. **跨上下文用窄接口。** 方法、信号、只读 ViewModel、端口；不要直接改对方内部字段。
4. **静态定义与运行时状态分离。** 定义放内容/配置资源，实例状态放运行时对象。
5. **动态对象有生命周期 owner。** 创建、注册、结束、清理不能靠“谁顺手谁做”；上下文地图必须写清。
6. **先修最痛的一条。** 不要一次重写全部；找耦合最高、最挡下一个功能的一条边界。
7. **不为 DDD 而 DDD。** 聚合根、仓储、工作单元、领域事件总线只在确实需要时引入。

## 操作顺序

1. 盘点现状
2. 定义上下文
3. 画上下文地图与依赖规则
4. 找边界违规
5. 排序并选第一个修正
6. 写 ADR / 上下文地图
7. 交给 execution-loop 连续执行

### 第一步：盘点现状

用代码库梳理（可用 `code-digest`）回答：

- 目录/模块实际拥有什么
- 入口/组合根是谁
- 哪些文件被最多模块依赖
- 哪些文件同时承担规则、编排、表现
- 哪些内容定义与运行时状态混在一起

不要凭记忆；以代码和文档为准。

### 第二步：定义上下文

每个上下文写两列：

| 拥有 | 不拥有 |
|---|---|
| 本上下文唯一负责的规则/状态 | 不应由本上下文决定的事 |

上下文数量控制在 5~8 个；小项目可以更少。不要按文件类型分（`utils`、`helpers` 不是上下文）。

### 第三步：画上下文地图

至少输出：

- 上下文清单
- 依赖方向图
- 允许/禁止的依赖表
- 共享内核（Shared）清单
- 跨上下文通信方式（方法/信号/端口/只读数据）
- 动态对象生命周期所有权：谁创建、谁注册、谁结束、谁清理、作用域
- 跨上下文事件：发出者、监听者、顺序、幂等

上下文地图是静态边界，不能单独证明运行时接线；高风险动态对象要配合状态图/时序图，具体图集按项目设计流程选择。

依赖规则要能用一句话说清，例如：

```text
Presentation 只读 Application 的 ViewModel；Domain 不引用 UI。
```

### 第四步：找边界违规

常见违规：

| 违规 | 现象 |
|---|---|
| 实体依赖内容目录 | 领域对象直接查内容/配置表 |
| 表现层知道领域 ID | UI 按具体条目 ID 分支 |
| 组合根承担规则 | 入口层写领域公式 |
| 双向依赖 | A 调 B，B 又回调 A 的内部方法 |
| 内容与状态混放 | 配置文件里存运行时状态 |
| 跨上下文直接改字段 | 直接写对方内部字段 |
| 动态对象绕过创建入口 | 派生/事件代码直接实例化对象，绕过统一生成服务 |
| 生命周期无 owner | 创建、注册、清理分散在多个调用点 |
| 事件只发不收 | 对象发出死亡/完成事件，但运行级注册表没有监听 |

> 示例（游戏）：角色实体直接查升级表、HUD 判断升级 ID、`.tres` 里存当前 HP/等级、直接写对方 `hp` / `cooldown`。

每条违规记录：现象、影响、修正、优先级。

### 第五步：排序并选第一个修正

排序依据：

1. 是否阻塞下一个功能
2. 是否造成双向依赖或全局耦合
3. 修复是否可独立测试
4. 修复成本是否可控

第一个修正应该是**小的、可验证的、能减少实际耦合的**。不要第一步就重写整个 `main`。

### 第六步：写 ADR / 上下文地图

记录：

- 背景与约束
- 上下文清单与所有权
- 依赖方向
- 已识别违规
- 本次修正范围
- 明确不做
- 止损条件

### 第七步：交给 execution-loop

把「本次边界修正」写成工作包，交给 `execution-loop` 连续执行；状态交给 `implementation-track`。

## 轻量 DDD vs 完整 DDD

| 采用 | 不默认采用 |
|---|---|
| 上下文地图 | 聚合根 |
| 所有权与依赖规则 | 仓储 / 工作单元 |
| 端口/适配器（按需） | 全局领域事件总线 |
| 共享内核（少量） | 模块化插件系统 |
| ADR 记录边界决策 | 为每个内容类型建 Repository |
| 先修一条最痛边界 | 一次性重写全部模块 |

拆分组合根与行为保持重构的方法、安全门见 `references/refactor-playbook.md`。



## 反模式

- 按技术层分上下文（`models`、`services`、`utils`）
- 把 `main` 叫 Application 就以为边界完成了
- 所有跨模块调用都上事件总线
- 为了「纯净」把简单逻辑拆成 5 层
- 只画上下文地图，不写动态对象的创建/注册/清理
- 只画类图，不画生命周期状态和时序，就认为边界已证明
- 只画图，不修第一条违规
- 边界规则无法用一句话说清

## 交接

- 设计阶段：`design-stage`；重构交付：`delivery-stage`
- 代码现状：`code-digest`
- 目标与分期：`roadmap-planning`
- 连续执行：`execution-loop`
- 验收状态：`implementation-track`
- 规则文档：`docs-core` / `game-docs`
- 产品表面 / 状态所有权：`experience-architecture`
- 收尾评审：`review`

## 边界

- 本 skill 只定义职责与依赖，不写具体业务行为规则。
- 不替代体验架构；屏幕/导航/产品状态归 `experience-architecture`，代码模块状态归本 skill。
- 不替代 Spec / 验收；行为结论仍回项目规则文档。
- 不强制完整 DDD；轻量方案优先。
- 边界修正必须先能测试，再动手。
