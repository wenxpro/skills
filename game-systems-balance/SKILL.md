# 游戏系统平衡

目标：先定义**目标体验与基准值**，再调数字；避免“拍脑袋改数值”。

本 skill 负责平衡方法与判据；战斗模型本身用 `game-combat-model`，验证实验与测试分层用 `validation-design`。

## 何时使用

- 战斗 TTK、胜率、克制预算、命中数
- 经济来源/消耗/转换、通胀、资源循环
- 成长/解锁/升级曲线、战力膨胀
- 难度曲线、AI 强度、失败/重试节奏
- 掉落/随机/保底
- 支配性、退化策略、敏感性分析

不适用：

- 单次数值微调，没有目标
- 完整 Spec/验收矩阵 → `game-docs`
- 代码审查 → `code-review`
- 单次试玩结果分类 → `feedback-stage`

## 行为

无主动打断。用户要求设计/审计系统平衡时使用；不主动评价日常单次数值调整。

## 核心规则

1. **先定目标，再定数字。** TTK、胜率、资源时间、难度通过率、成长阶段，都先写目标区间。
2. **分系统处理。** 战斗、经济、成长、难度、随机性各有自己的基准，不要用一套数字解释所有。
3. **基准 + 区间。** 用 P50/P90、胜率区间、时间区间，不用单次结果。
4. **支配性检查。** 某个单位/策略在所有对局都不劣，就是支配；先修支配，再谈微调。
5. **消融/反事实。** 去掉一个机制后结果不变，机制可能只是装饰。
6. **经济看来源、消耗、转换。** 只有来源没有 sink = 通胀；只有 sink 没有来源 = 卡死。
7. **成长看相对战力。** 成长应改变打法，而不是只放大数值；检查战力膨胀与内容追赶。
8. **难度看可归因失败。** 玩家失败应能说出原因；不要用数值墙/作弊制造难度。
9. **一次只改一个变量。** 改完跑 sim/bot/回归，再改下一个。
10. **基准值要版本化。** 记录 build、seed、样本量、P50/P90，避免用旧基准证明新版本。

## 审计清单

- [ ] 目标 TTK/胜率/资源时间/难度通过率写了吗？
- [ ] 是否只看平均值，没有 P90/失败分布？
- [ ] 是否存在支配性单位/策略/投资？
- [ ] 去掉某个机制后结果是否不变？
- [ ] 经济是否有来源、消耗、转换、回收？
- [ ] 成长是否改变打法，还是只放大数值？
- [ ] 难度是否可归因，而不是数值墙/作弊？
- [ ] 调参表是否与运行时配置一致？
- [ ] 基准值是否版本化、可复现？
- [ ] 是否一次改了多个变量？

## 输出

- 平衡表：`templates/balance-sheet.md`
- 调参矩阵：单位/系统 × 指标 × 目标 × 实测
- 支配性/消融结果
- 结论：通过 / 调参 / 重做模型

## 反模式

- 先改数字再找目标
- 用一次 sim/一局结果证明平衡
- 只调平均值，不看尾部/失败分布
- 只加数值，不改变打法
- 经济没有 sink 或没有 source
- 难度靠 AI 作弊/锁血/数值墙
- 同时改频率、伤害、HP、克制
- 用旧基准证明新版本

## 交接

- 战斗模型：`game-combat-model`
- 验证实验：`validation-design`
- 测试分层：`validation-design`
- Spec/验收：`game-docs`
- 试玩结果：`feedback-stage`

## 边界

- 不写项目具体数值；数值写项目配置/文档
- 不替代 `game-docs` 的 Spec/验收
- 不替用户拍板“好不好玩”；给可验证的平衡判据
