# 文档体系核心规则

目标：每类内容只有一个归属文档，每次变更只改该改的地方。本 skill 只定义文档结构和变更规则，不提供模板；模板与领域规则由具体 skill（如 `game-docs`）提供。

> 槽位到编号/文件的映射在 `standards.md`，替换它即可适配不同领域。

## 文档槽位

任何项目的文档体系由 7 个槽位组成，数量可减、职责不可混：

| 槽位 | 回答的问题 | 内容 |
|---|---|---|
| 入口 | 从哪开始看？ | 索引、状态、导航、变更流程 |
| 假设 | 为什么做这个？验证什么？ | 一页纸目标、范围、止损条件 |
| 规则 | 具体行为是什么？ | 可判定的行为规则，每条有 ID |
| 验收 | 怎么判定做完了？ | 可执行用例，映射回规则 ID |
| 决策 | 为什么这么选？ | ADR：备选、对比、否决理由 |
| 证据 | 验证结果如何？ | 评审记录、试玩/测试结果 |
| 检查 | 什么时候算完成？ | DoD、自检清单 |

槽位可按项目裁剪（小项目可无 ADR 目录），但不能让同一事实出现在两个槽位。

## 单一事实源

- 行为在「规则」，验收在「验收」，证据在「证据」
- 其他文档只引用，不复制内容
- 规划只排期、跟踪只更新状态、评审只写结论——都不重写规则

## 行为变更三件套

任何行为变更，按顺序：

1. 改「规则」，更新规则 ID
2. 改「验收」，增加/修改对应用例
3. 写变更记录

方向/架构级变更追加：新 ADR + 评审。

不允许：只改代码不改规则、只改规则不改验收、口头承诺不落记录。

## 阈值与基准值变更

行为变化会让旧基准值/阈值失效。处理顺序：

1. 在验收/回归文档明确标注旧基准值作废，不继续引用
2. 用相同的样本设计重跑（种子/模型/时长/环境）
3. 回填新值，并记录旧值、新值、原因、样本、日期
4. 不能为了让测试通过而静默放宽阈值；先判断是实现错误、测试错误还是设计变化

样本不足时输出显式 `SKIP`，`SKIP` 不算通过。

本节只定义文档记录要求；代码审查与合并前检查见 `code-review`。

## ADR 实施记录

ADR 不是写完就结束。实施后补一行/一节：

- 实际结果（不是计划）
- 证据（测试、回归、性能、提交）
- 与估算/预期的偏差
- 未关闭的后续项

估算不是承诺；实际偏离要留痕，不回头把原估算改成实际值。

## ADR 归档

归档标准（满足其一）：

- 已被新 ADR 取代
- 已执行完成，且不再约束当前版本
- 决策范围已不存在

**已实现但仍定义当前行为的 ADR 保持 active**；不要按“完成即归档”把当前约束藏进 archive。归档索引写原因和替代 ADR。

## 状态语义

- 文档状态：`Draft / Proposed / Accepted / Conditional / Superseded`
- 验收状态：`◻ 未开始 / 🔄 进行中 / ✅ 通过 / ❌ 失败`
- 评审结论：`通过 / 有条件通过 / 否决`（归档：`Superseded / Archived`）
- 优先级：P0/P1 只用于验收；功能/包优先级用 `High / Medium / Low`

## 不适用

- 创建或维护具体项目文档（游戏用 `game-docs`，软件项目按仓库约定）
- 多角色评审（用 `review`）
- 文档集一致性审核（用 `docs-audit`）
- 排期与状态跟踪（用 `roadmap-planning` / `implementation-track`）

## 边界

- 不提供模板与领域规则；模板由领域 skill 提供
- 不改项目内容，只定义文档结构和变更规则
- 不替代 Spec / 验收；同一事实不能出现在两个槽位

## 导航

- 游戏项目文档模板 → `game-docs`
- 产品表面 / 屏幕流 / 状态所有权 → `experience-architecture`
- 评审 → `review`
- 文档集审核 → `docs-audit`
- 代码审查 / 合并前检查 → `code-review`
- 规划 / 跟踪 → `roadmap-planning` / `implementation-track`
