# 文档集审核

按下面的清单逐项过一遍文档集，最后输出审核报告。审核的目标是「每篇文档的每个结论都可信、可复核、不重复」。

> 个人风格规范（翻译腔判断标准、验证表述约定、mermaid 写法）在 `standards.md`，其他团队可整体替换为本团队标准。

## 何时使用

- 文档集评审、发布前
- 外部事实变化后（上游新版本、标准更新、竞品动态），核对既有结论是否仍成立
- 读者抱怨文档「读着难受、不像人话」时，检查表述问题

## 适用范围

适用于多篇文档相互引用、共享术语与编号体系、结论依赖外部事实（软件版本、市场数据）的文档集。单篇独立文档只需抽查，不需要完整流程。

## 操作顺序

1. 先用 grep 并行扫全库（交叉引用、术语、版本号、编号），建立疑点清单
2. 再读疑点所在文件的相关段落核实
3. 修复后复扫一遍确认零残留
4. 最后对改动文件跑 diagnostics 确认无语法错误

## 第一步：交叉引用一致性

1. 收集所有「第 X 部分」「第 X 节」「见 xx.md」引用，逐一验证目标存在且编号正确
2. 收集文档集自定义的编号体系（决策编号、需求编号、章节编号等），确认定义处与引用处一致
3. 结构重排后（合并章节、前移编号），必须全库 grep 旧编号残留
4. 文档头部标注的依据范围（版本号、核实日期）必须覆盖正文引用的最新事实，只标注不覆盖就是不一致

## 第二步：翻译腔与术语

检查术语是否自然、有无翻译腔。判断标准（逐词直译、生造组合词、反例放过）见 `standards.md`「翻译腔与术语」。

用户对翻译腔敏感时，先列出发现清单再逐处替换；拿不准的词先问用户，不擅自发明译法。

## 第三步：版本锚点与事实时效

1. 事实性断言尽量带版本锚点（「vX.Y 起」「在哪个版本反转」），读者能自己复核
2. 时效性数据（stars、订阅数、市场数据、日期）标注实测日期；重新核实到显著变化时更新数值与日期
3. 外部事实变化后，只审「哪些结论被触及」，不逐条追新、不把文档写成 changelog
4. 新事实按性质分流：修正结论 → 写进行内正文；证实结论 → 一句带过或集中记录；与结论无关 → 丢弃

## 第四步：验证表述规范

结论的正确性不靠语气，靠验证链。检查四条约定（判断与事实分写、演进故事不写断言、反面验证优先、预测标注验证状态），详细定义见 `standards.md`「验证表述」。

判断与事实是否分写、结论是否可复核、预测是否标注验证状态，是这一步的三个核对点。

## 第五步：图表覆盖

1. 长段落描述机制关系（管线、分层、时序、矩阵、依赖方向）的地方应有 mermaid 图
2. 每张图前写一句读图引导，说明图在回答什么
3. 检查 mermaid 语法：写法约定见 `standards.md`「mermaid 写法」
4. 图与正文分工：图只画关系，细节仍在正文；保留文字版步骤清单时不删

## 第六步：重复内容

1. 同一对比表或结论在多篇出现时，确认是「引用」关系而非重复维护
2. 分析类内容：案例事实进坐标对比表，启示按主题合并成观察条目，不保留独立案例章节
3. 摘要表与正文论证的重复可接受（摘要指向正文），但摘要引用的编号必须与正文一致

## 第七步：数字核对

1. 汇总数字（「共 N 条」「N+M 条」）必须实际数一遍，不能轻信之前的记录
2. 同一事实在不同文档里的数字要一致，不一致时以最新实测为准

## 第八步：实现后漂移扫描

里程碑或一批实现落地后，专门扫一遍“最容易过期的当前事实”：

1. 当前范围/能力表（做/不做，已实现/计划）
2. 公式、常量、上限、默认值
3. 场景/配置相关数值（如不同环境、难度或模式；不要把某场景的数字写成通用事实）
4. 汇总数量（内容项、功能、模块、测试、资源）
5. 代码符号、文件路径、模块树、命令行参数
6. 验收 ID 范围与跨文档引用
7. 版本号、状态、索引表、变更记录
8. 历史基准值章节是否仍被读成当前规则

规则：历史证据保留当时的日期/版本，不追改；当前状态表必须用最新实测值。代码实现事实以 `code-digest` 的结论为输入；本步只负责文档侧的漂移清单。

## 第九步：ID 覆盖矩阵

对编号体系做三向核对，输出缺口表：

- 规则/设计中有定义，但验收没有对应用例
- 验收中有用例，但规则没有定义
- 其他文档引用了，但定义处不存在
- 重复编号、范围写法与实际集合不一致

可用 `scripts/check-id-coverage.ps1` 对两份文档做集合比较，再人工确认语义。

## 边界

- 只看可复核性，不问语气；不改设计结论——设计提案先问用户，不借「订正」写进文档
- 不替用户拍板取舍；报告里给证据和建议即可
- 不改代码；代码事实以 `code-digest` 的结论为输入
- 修复前先输出报告；修复后必须复扫，零残留才算完成

## 输出

先输出审核报告，修复完成前不改文档。报告分三组：

- **必须修**：事实错误、引用断裂、依据范围不符、编号残留
- **建议修**：翻译腔、缺图、缺验证状态标注
- **核对无误**：列出核对的项，证明真的查过

### 事实订正 vs 设计提案

- **事实订正**：有代码/测试/资源/外部事实支撑，可直接改，带版本锚点。
- **设计提案**：改变行为、范围、优先级或取舍，必须先经负责人确认；不要借“订正”写进规则文档/ADR。
- 审核报告把两类分开列；设计提案放“待决”，不直接落文档。

修复并复扫、跑过 diagnostics 后，把结果汇总给用户，询问下一步（提交、继续修订或其他）。
