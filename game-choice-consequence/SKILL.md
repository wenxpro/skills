# 选择与后果系统

目标：让选择**有信息、有代价、有回声**，而不是三选一后只换一句台词。

本 skill 负责选择/状态/后果/回访/结局的系统设计；故事内容与世界观用 `narrative-docs`，关卡布局用 `level-encounter-design`，数值用 `game-combat-model`。

## 何时使用

- 设计道德选择、经营取舍、角色关系、回访、结局分支
- 需要选择状态表、回访矩阵、结局条件
- 排查「选择没区别」「后果看不见」「分支写不完」「结局收不拢」

不适用：

- 故事/对白/世界观文档 → `narrative-docs`
- 关卡/遭遇布局 → `level-encounter-design`
- 战斗数值/经济平衡 → `game-combat-model` / `game-systems-balance`
- UI 菜单/排版 → `ui-baseline`

## 行为

参考型 skill，无主动打断。用户要求设计/审计选择与后果时使用。

## 核心规则

### 1. 选择首先是决策，不是问答

- 玩家在选什么：价值观、风险、资源、关系、信息？
- 选项之间要有真实取舍；没有代价的选项只是台词。
- 不要用「善良/邪恶」标签代替具体后果。
- 选项数量服务决策；三选一不是默认答案。

### 2. 状态模型是单一事实源

- 用明确的标记/计数/关系/物品/知识表示选择结果。
- 状态字段有类型、默认值、生命周期；不要用散落布尔。
- 选择写入状态，后果读取状态；不要反过来在 UI 里临时判断。
- 状态变更要有日志，便于回放/调试/QA。

### 3. 信息差与可读性

- 区分：玩家知道、角色知道、系统知道。
- 选择前给足够信息做判断，但不一定给结果。
- 后果要可归因：玩家能说出「因为我之前做了什么」。
- 隐藏信息可以制造惊喜，但不能制造无预警的惩罚。
- 灰度/静音/不同语言下仍能理解选择。

### 4. 延迟与回访

- 选择不必立刻结算；延迟回访让选择有回声。
- 定义回访时机、触发条件、访问次数、错过后果。
- 回访矩阵：谁回来、为什么回来、状态如何变化、玩家能否认出。
- 不要写「只有开发者知道的孤儿分支」；每个分支有入口/出口。
- 回访要能被玩家感知：称呼、物品、关系、环境变化。

### 5. 后果层级

| 层级 | 例子 | 风险 |
|---|---|---|
| 即时 | 台词/价格/物品 | 只像反馈 |
| 延迟 | 回访/关系变化 | 玩家忘记来源 |
| 系统 | 商店/阵营/路线 | 难回滚 |
| 结局 | 结局/评价 | 收敛困难 |

- 至少有一层是非即时的；否则选择没有重量。
- 后果不要只靠文本；用系统/关系/资源体现。
- 强后果要给玩家恢复/补救路径，除非明确不可逆。

### 6. 结局收敛

- 结局条件写清楚；优先级/互斥/兜底明确。
- 不要让某个早期选择永久锁死所有结局，除非是明确设计。
- 结局要回应主要选择，而不是只回应最后一个选项。
- 用状态快照/回放验证所有结局可达；避免不可达/被覆盖的结局。
- 结局数量服务表达，不是越多越好。

### 7. 内容与数据分离

- 选择表、状态表、回访表、结局表分开；writer 可读。
- 文本/本地化走文案表；逻辑 ID 稳定。
- 条件用数据/表达式，不写死在 UI 脚本。
- 版本变更时保留旧状态迁移/默认值。

### 8. 证据

- 选择/状态矩阵：每个选项写入什么、读取什么。
- 回访矩阵：触发、次数、错过。
- 结局覆盖：自动遍历或脚本验证所有结局可达。
- 试玩：玩家是否理解、是否后悔、是否想重玩。
- 截图只能证明 UI 文案，不能证明选择有重量。

## 检查清单

- [ ] 每个选择有真实取舍，不是标签问答
- [ ] 状态字段有类型/默认值/生命周期/日志
- [ ] 玩家知道/角色知道/系统知道区分清楚
- [ ] 选择前信息足够，后果可归因
- [ ] 至少一层延迟后果/回访
- [ ] 回访有触发/次数/错过/可感知
- [ ] 结局条件、优先级、兜底明确
- [ ] 所有结局/分支可达，无孤儿
- [ ] 文本与逻辑分离，本地化 ID 稳定
- [ ] 有选择矩阵、回访矩阵、结局覆盖证据
- [ ] 真人试玩验证理解与后悔，而非只看截图

## 输出

- 选择/状态模型：`references/choice-state-model.md`
- 回访与结局：`references/return-and-endings.md`
- 选择矩阵模板：`templates/choice-matrix.md`

## 反模式

- 选项只有文案差异，状态不变
- 用善恶标签代替后果
- 所有后果即时结算，没有回声
- 回访只有开发者知道，玩家认不出
- 早期选择永久锁死所有结局
- 结局只回应最后一个选项
- 分支没有入口/出口，写完收不拢
- 用截图证明选择有重量

## 交接

- 故事/对白/世界观 → `narrative-docs`
- 关卡/遭遇 → `level-encounter-design`
- 数值/经济 → `game-systems-balance` / `game-combat-model`
- 选择 UI/排版 → `ui-baseline`
- 验证计划/证据 → `validation-design`
- 项目规则/验收 → `game-docs`

## 边界

- 不写具体项目的天数、价格、顾客类型、结局名
- 不替代故事内容、关卡、数值、UI
- 不把「多结局」当目标；先保证选择有重量
- 不可逆后果必须明确告知/可解释
