# 单会话多仓库提交

目标：一次任务改多个仓库时，每个仓库独立提交、独立推送、独立验证；不把多仓库当成一个原子事务。

## 何时使用

- 一个任务同时改了多个独立仓库
- 不同域名/凭据的仓库需要分别推送
- 需要汇报每个仓库的提交、推送和验证状态
- 一个仓库的变更依赖另一个仓库的提交

不适用：

- 单仓库提交 → `git-commit`
- 同仓库多个 worktree → `worktree-workflow`
- 代码审查 → `code-review`
- 设计/范围决策 → `review` / `design-stage`

## 核心模型

- Git 提交是**仓库级**的；不存在跨仓库原子提交。
- 每个仓库有自己的分支、remote、凭据和工作区状态。
- 先按仓库分组，再逐仓库提交；部分成功是正常结果。
- 不把 A 仓库的变更混进 B 仓库
- 跨仓库变更前先确认接口版本与合并顺序；接口登记与集成计划见 `cross-project-integration`。
- 不替用户提交未确认的脏工作区。
- 每个仓库的写任务默认在自己的 worktree 内完成；本 skill 只负责按仓库提交和推送。

## 0. 预检

先列出所有涉及仓库：

| 仓库 | 路径 | 分支 | remote | 工作区 | owner |
|---|---|---|---|---|---|
| A | `<repo-a>` | `main` | `<remote-a>` | clean / dirty | 谁负责 |
| B | `<repo-b>` | `main` | `<remote-b>` | clean / dirty | 谁负责 |

每个仓库至少检查：

```bash
git -C <repo> status --short --branch
git -C <repo> remote -v
git -C <repo> branch --show-current
git -C <repo> log --oneline -1
```

不同域名/凭据时，先验证认证：

```bash
ssh -T git@<host>
```

或确认该仓库的 credential helper 可用。

## 1. 分组

- 按仓库分组，不按时间或文件类型跨仓库混提交。
- 一个仓库内可以按性质拆多个提交。
- 跨仓库有依赖时，按依赖顺序：
  - 被依赖的库/规范仓库先提交
  - 使用方仓库后提交
  - 描述行为的文档跟随代码仓库，或紧接其后
- 只暂存本次任务的文件；工作区有用户未提交内容时，不默认 `git add -A`。
- 无法判断某个文件是否属于本次任务时，先问用户。

## 2. 逐仓库提交

对每个仓库执行：

1. **看变更**：`git -C <repo> diff -- <paths>`、`git -C <repo> diff --cached`
2. **暂存明确路径**：`git -C <repo> add <paths>`
3. **提交**：按 `git-commit` 的 message 规范
4. **记录 hash**：`git -C <repo> rev-parse HEAD`
5. **推送**：`git -C <repo> push origin <branch>`
6. **验证远端**：`git -C <repo> ls-remote origin <branch>`
7. **记录状态**：clean / 仍有用户改动 / 推送失败

不要用一条命令跨仓库提交；每个仓库单独执行。

## 3. 部分失败

多仓库推送不是原子的，失败是正常状态：

- 一个仓库成功、另一个失败时，不要声称“全部已推送”。
- 只重试失败的仓库；已成功的不要重复提交。
- 网络/认证失败和代码/测试失败分开记录。
- 不 force push、不重写历史来“修复”部分失败。
- 推送成功后仍有用户未提交文件，要明确标注“未包含在本次提交”。

## 4. 跨仓库一致性

- 同一个任务/issue/ADR 的编号写进各仓库 commit message。
- 仓库 A 依赖仓库 B 的版本时，在总结里记录 B 的 commit hash。
- 代码仓库与文档仓库同时变更时，确保文档引用的是本次代码提交，而不是旧版本。
- 同一个变更不要在两个仓库重复实现；指定唯一 owner
- 提交前确认接口登记表版本一致；只提交一侧会让下游失效。
- 一个仓库的变更会让另一个仓库失效时，停下来报告，不要继续推。

## 5. 汇报格式

至少给出：

| 仓库 | 分支 | commit | push | 远端验证 | 备注 |
|---|---|---|---|---|---|
| A | `main` | `<hash>` | 成功/失败 | `ls-remote` 一致 | 未提交文件 |
| B | `main` | `<hash>` | 成功/失败 | `ls-remote` 一致 | 部分失败重试 |

补充：

1. 哪些文件没有提交、为什么
2. 失败仓库的重试命令
3. 跨仓库依赖与版本
4. 下一步

## 反模式

- 把多个仓库当成一个原子提交。
- 一个 `git add -A` 扫过多个仓库。
- 推成功一个仓库就汇报“全部完成”。
- 把用户未提交的工作混进本次提交。
- 不同域名共用同一套凭据，失败后反复重试。
- 用 force push 处理部分失败。
- 不验证远端就宣布推送成功。
- 文档和代码同时改，却不互相引用。
