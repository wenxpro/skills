# 课题调研规范（个人/团队风格标准）

本文件存放 `topic-research` 中依赖具体项目习惯的部分。本仓库（cheese/pi-agent 项目文档集）的约定如下，其他团队可整体替换。

## 调研入口偏好

- GitHub API（api.github.com）优先于 github.com 页面：contents 接口拿目录/文件结构，search 接口按 star 排序看生态（`https://api.github.com/search/repositories?q=topic:<主题>&sort=stars&order=desc`），单文件优先 raw.githubusercontent.com，失败时退回 api 的 base64 内容字段
- 需要读真实实现时本地 clone（/Volumes/BAK/work 下），clone 前先确认目录不存在、不污染项目工作区
- 第三方依赖声明（package.json / Cargo.toml）是技术栈判定的第一证据
- 本地能装能跑的产品优先行为观察（B 级），安装验证用临时目录隔离配置，不落真实 key

## 证据标注格式

写进文档的结论带日期与实测方式后缀：

- 「（2026-08-09 源码结构实测）」「（2026-08-09 依赖清单实测）」「（2026-08-09 行为观察）」
- 推断必须显式写「推断」或「未验证」，例如「opentui 未稳定是推断，需以版本演进验证」

## 文档落点约定

调研结论按性质落位（与本项目文档集约定一致）：

- 生态/竞品事实 → 设计总纲 1.4/1.5（行业坐标系），不建独立案例分析
- 技术选型论证 → 各包 DESIGN.md（就近工程）
- 交互/体验调研 → tui DESIGN.md 第五节
- 新事实证实既有结论 → 原文一句带过，不建独立文档
- 与结论无关 → 丢弃

## 调研纪律

- 课题未界定前不动手
- 全景未建立前不深入单点
- 结论必须有证据等级，无证据就是推断
- 文档已写入的结论被新证据推翻时，先改文档再说明，不保留错误结论
- 调研途径先于结论：用户指出途径有问题时，重新从全景做起，不在原路径上修补
- 教训案例：曾仅凭包名与目录结构推断某 TUI 框架「是 SolidJS 写的响应式框架」，未读其 README——实际是 Zig 原生核心 + 多语言绑定。推断不等于验证
