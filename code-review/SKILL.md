# 代码审查与合并前检查

目标：在测试之外找出真实缺陷，并确认「这次改动该跑的检查」真的跑了。审查不是代码风格检查，也不是把测试全绿复述一遍。

## 何时使用

- 功能、修复、重构完成后，提交/合并前
- 改动了数值、配置、状态重置、计时/随机数、UI 数量或刷新频率、内容表等高风险面
- 测试全绿但怀疑测试没有覆盖真实行为
- 行为变化导致旧基准值/阈值失效，需要重定
- 需要判断「能不能合并/发布」

不适用：

- 设计、方案、里程碑评审 → `review`
- 文档集交叉引用、过时、重复 → `docs-audit`
- 验收状态与偏差回写 → `implementation-track`
- 纯格式/lint/类型检查 → 交给工具，不占审查结论

## 核心规则

1. **先读目标，再读 diff。** 先确认目标、验收项和改动范围，不凭记忆审。
2. **每个问题都要有依据。** 级别、位置、影响、复现/日志/测试、建议改法；没有依据的直觉降级为「待验证问题」。
3. **必须修的问题没清零，不通过。** 错误结果、崩溃、数据损坏、重开结果不一致、静默失败、不可逆风险，修完并复跑才算通过。
4. **只审这次改动和它的直接影响。** 顺手发现的问题记录，不扩大本次范围。
5. **测试全绿不等于审查通过。** 还要看断言是否真的能失败、失败路径是否覆盖、样本是否足够。
6. **修完要复跑。** 至少重跑失败用例 + 相关检查；不靠「改完应该好了」。
7. **不能靠放宽阈值让检查变绿。** 行为变化使旧基准值失效时，重跑、回填、说明旧值作废；不静默放宽阈值。
8. **不隐藏失败。** 失败要么修，要么标为未关闭；跳过和样本不足不能算通过。

## 审查流程

1. **确认范围**：目标/验收项、diff 范围、上次基准值、现有测试。
2. **判断风险**：按「改了什么 → 必须跑什么检查」选检查项，见下表。
3. **读代码**：控制流、状态归属、边界条件、失败路径、资源生命周期、并发/时序。
4. **跑检查**：先跑最小相关用例，再跑受影响检查；记录命令、样本和结果。
5. **写问题**：按必须修/建议修/可选分级；必须修的问题给出改法。
6. **修复和复跑**：修复 → 复跑 → 更新结论；必要时同步规则文档/验收/ADR/基准值。
7. **交接**：检查通过后提交；验收变化回写跟踪；文档变化走文档检查。

## 改了什么 → 必须跑什么检查

| 改动类型 | 必须跑的检查 | 常见漏点 |
|---|---|---|
| 行为/规则 | 行为测试 + 对应验收用例 | 只改代码，不改规则文档/验收 |
| 数值/配置 | 配置校验测试：字段存在、范围、跨字段约束 | 代码里还有硬编码；默认值和配置文件不一致 |
| 状态重置/计时/随机数 | 重开一致性测试：同一实例重复运行，关键指标一致 | 只比较两个新进程；reset 后残留节点/计时器 |
| UI 数量/刷新频率 | 数量上限、合并、刷新频率 + 性能测试 | 每帧全量遍历；标记数量随实体数线性增长 |
| 内容表/资源表 | 内容校验 + 文档检查 | ID 重复、引用缺失、旧数据没作废 |
| 性能关键路径 | 性能测试：P50/P95/峰值 + 样本量 | 只看单一平均值；样本太小或没固定种子 |
| 测试代码 | 反向用例/失败注入 | 断言永远为真、样本不足却跳过、只测 mock |

> 具体阈值、命令和样本量放 `standards.md` 的检查清单；检查项编号由项目规范定义，本 skill 不绑定编号。

## 问题分级

| 级别 | 判据 | 处理 |
|---|---|---|
| 必须修 | 错误结果、崩溃、数据损坏、重开结果不一致、静默失败、安全/不可逆风险 | 修完并复跑后才能通过 |
| 建议修 | 边界条件、可维护性风险、缺失测试、性能退化但不影响合并 | 本次修或记录排期 |
| 可选 | 命名、结构、重复、可读性 | 可后置，不阻塞 |

> 不使用 P0/P1 表示代码问题；P0/P1 只表示验收优先级（见 README 共用约定）。

## 测试质量检查

- 断言对应哪条规则/验收项？实现写错时它会不会失败？
- 是否覆盖边界：空输入、0、上限、重复、重开、并发/时序？
- 是否有测试被跳过、样本不足却静默 PASS？
- 是否有测试间共享状态、顺序依赖、真实时间等待？
- 是否只测 mock，没测真实集成？
- 测试通过时是否还有错误日志/警告？错误日志也算失败信号。
- 失败重试是否超过约定次数？flaky 测试按缺陷处理，不靠重跑掩盖。

## 输出内容

审查结束必须报告：

1. 范围和基准（目标、diff/提交、没覆盖的部分）
2. 检查执行表（改动类型、命令、样本、结果）
3. 问题列表（ID、级别、位置、影响、依据、建议）
4. 结论：通过 / 有条件通过 / 不通过
5. 复跑记录（改了什么、重新跑了什么）
6. 剩余风险和后续项

记录写入项目文档或 `templates/code-review.md`；不写进 skill 目录。

## 边界与反模式

- 不替用户改需求/设计；发现设计问题转 `review`。
- 不顺手重构无关代码；不把审查变成风格争论。
- 不以「测试全绿」代替审查，也不以「审查通过」代替测试。
- 不删除失败测试、不降低断言、不靠放宽阈值换绿色。
- 不把项目名、引擎、具体数值写进通用层；放 `standards.md` 的项目类型检查清单或项目规范。
