# 代码审查与变更门禁

目标：在测试之外找出真实缺陷，并确保「这次改动该跑的验证」真的跑了。审查不是风格检查，也不是把测试全绿复述一遍。

## 何时使用

- 功能、修复、重构完成后，提交/合并前
- 改动了数值、配置、状态重置、计时/RNG、UI 预算、内容表等高风险面
- 测试全绿但怀疑测试没有覆盖真实行为
- 行为变化导致旧基线/阈值失效，需要重定
- 需要判断「能不能合并/发布」

不适用：

- 设计、方案、里程碑评审 → `review`
- 文档集交叉引用、过时、重复 → `docs-audit`
- 验收状态与偏差回写 → `implementation-track`
- 纯格式/lint/类型检查 → 交给工具，不占审查结论

## 核心规则

1. **先读意图，再读 diff。** 先确认目标、验收项和变更范围，不凭记忆审。
2. **每条发现必须有证据。** 级别、位置、影响、复现/日志/测试、建议修法；没有证据的直觉降级为「待验证问题」。
3. **阻断项未清零不通过。** 错误结果、崩溃、数据损坏、确定性破坏、静默失败、不可逆风险，修完并复验才算通过。
4. **只审变更及其直接影响。** 顺手发现的问题记录，不扩大本次范围。
5. **测试全绿不等于审查通过。** 还要看断言是否真的能失败、失败路径是否覆盖、样本是否足够。
6. **修复后复验。** 至少重跑失败用例 + 相关门禁；不靠「改完应该好了」。
7. **阈值不能用来掩盖失败。** 行为变化使旧基线失效时，重跑、回填、说明旧值作废；不静默放宽阈值。
8. **不隐藏失败。** 失败要么修，要么标为阻塞/未关闭；跳过和样本不足不能算通过。

## 审查流程

1. **建立基线**：目标/验收项、diff 范围、上次基线、现有测试。
2. **风险分类**：按「变更类型 → 必跑证据」选门禁，见下表。
3. **读代码**：控制流、状态所有权、边界条件、失败路径、资源生命周期、并发/时序。
4. **跑证据**：先跑最小相关用例，再跑受影响门禁；记录命令、样本和结果。
5. **输出发现**：按阻断/重要/建议分级；阻断项给出修复建议。
6. **修复与复验**：修复 → 重跑 → 更新结论；必要时同步契约/验收/ADR/基线。
7. **交接**：审查通过后提交；验收变化回写跟踪；文档变化走文档检查。

## 变更类型 → 必跑证据

| 变更类型 | 必跑证据 | 常见漏点 |
|---|---|---|
| 行为/规则 | 契约测试 + 对应用例 | 只改代码，不改契约/验收 |
| 数值/配置 | 配置契约测试：字段存在、范围、跨字段不变量 | 逻辑里仍有硬编码；默认值与配置文件不一致 |
| 状态重置/计时/RNG | 确定性/重开测试：同一实例重复运行关键指标一致 | 只比较两个新进程；reset 后残留节点/计时器 |
| UI/可视化预算 | 预算测试：数量上限、聚合、刷新频率 + 性能基线 | 每帧全量遍历；标记随实体数线性增长 |
| 内容/资源表 | 内容校验 + 文档检查 | ID 重复、引用缺失、旧数据未作废 |
| 性能敏感路径 | 性能基线：P50/P95/峰值 + 样本量 | 只看平均 FPS；样本太小或未固定种子 |
| 测试本身 | 反向用例/失败注入 | 断言恒真、样本不足静默跳过、只测 mock |

> 具体阈值、命令和样本量放 `standards.md` 的 profile；门禁 ID 由项目规范定义，本 skill 不绑定编号。

## 发现分级

| 级别 | 判据 | 处理 |
|---|---|---|
| 阻断 | 错误结果、崩溃、数据损坏、确定性破坏、静默失败、安全/不可逆风险 | 修复并复验后才能通过 |
| 重要 | 边界条件、可维护性风险、缺失测试、性能退化但不阻断 | 本次修或记录排期 |
| 建议 | 命名、结构、重复、可读性 | 可后置，不阻塞 |

> 不使用 P0/P1 表示代码审查级别；P0/P1 只表示验收优先级（见 README 共用约定）。

## 测试质量检查

- 断言对应哪条契约？实现写错时它会不会失败？
- 是否覆盖边界：空输入、0、上限、重复、重开、并发/时序？
- 是否有测试被跳过、样本不足却静默 PASS？
- 是否有测试间共享状态、顺序依赖、真实时间等待？
- 是否只测 mock，没测真实集成？
- 测试通过时是否仍有错误日志/警告？错误日志也算失败信号。
- 失败重试是否超过约定次数？flaky 测试按缺陷处理，不靠重跑掩盖。

## 输出契约

审查结束必须报告：

1. 范围与基线（目标、diff/提交、未覆盖部分）
2. 门禁执行表（变更类型、命令、样本、结果）
3. 发现列表（ID、级别、位置、影响、证据、建议）
4. 结论：通过 / 有条件通过 / 不通过
5. 复验记录（修了什么、重跑了什么）
6. 剩余风险与后续项

记录写入项目文档或 `templates/code-review.md`；不写进 skill 目录。

## 边界与反模式

- 不替用户改需求/设计；发现设计问题转 `review`。
- 不顺手重构无关代码；不把审查变成风格大战。
- 不以「测试全绿」代替审查，也不以「审查通过」代替测试。
- 不删除失败测试、不降低断言、不静默放宽阈值来换绿色。
- 不把项目名、引擎、具体数值写进通用层；放 `standards.md` profile 或项目规范。
