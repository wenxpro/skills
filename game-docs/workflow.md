# 工作流

按任务选一节，不要一次读全部。模板都在 `references/templates/`。

## 1. 初始化项目文档

适用：新项目；或已有文档散、过时、不可验收。

先问，不要猜：目标路径、项目名、类型、核心动词（只能一个）、当前里程碑（默认 M0 立项）。

1. 检查目标目录：`docs/` 已存在且非空时，先读 `00-README.md`，问用户覆盖 / 合并 / 换目录；不要默认 `-Force`。
2. 生成骨架：`new-project-docs.ps1`（参数见 `scripts/README.md`）；非 Windows 手动复制 `references/templates/`。
3. 填 `01-run-brief.md`：一页纸（一句话、单局参数、核心循环、灰盒范围、验证问题、止损条件），不写未来内容。
4. 如需要写 `04-adr/0001-core-verb.md`：备选、对比、反方意见、止损条件。
5. 自检：`check-docs.ps1`。
6. 停止：01 未被用户确认前，不写 02 / 03。

完成标准：结构完整（00~07）；01 能说清「这一局是什么」；关键方向有 ADR；检查通过。

## 2. 写 / 更新 Design Spec

适用：01 已确认；Spec 与实现不一致；新增系统前先定义行为。

读取：`references/templates/02-design-spec.md`、目标项目 `01-run-brief.md`、`00-README.md`。

1. 锁范围：本里程碑做 / 不做什么，未来内容放「开放问题」。
2. 写支柱：3~4 条，每条能用来否决需求。
3. 写状态机：状态表、转换表、暂停规则（哪个状态暂停游戏时间、哪个 UI 仍可交互）。
4. 写输入：哪个状态接受哪些输入；斜向归一化、UI 拦截、失焦处理。
5. 写核心系统：每个系统属性 → 行为 → 结算 → 反馈 → 边缘情况；每条规则给 ID；公式写清，数值标「首版假设」。
6. 同步验收：每条 P0 规则在 `03-acceptance.md` 有对应用例，没有用例 = 没写完。
7. 写变更记录：文末更新版本 / 日期 / 变更。
8. 自检：`check-docs.ps1`。

不要把：实现细节写进 Spec；未验证数值写成结论；「手感好」当规则；一次写完所有系统却不跑灰盒。

## 3. 验收矩阵

适用：02 已有行为规则；灰盒完成要跑 P0/P1；新增 / 修改用例。

读取：`references/templates/03-acceptance.md`、目标项目 `02-design-spec.md`。

1. 建立映射：逐条扫 02 的 P0 规则，每条至少一个 `AC-<类别>-<序号>`；缺失标 gap，不假装覆盖。
2. 写用例：前置（状态、种子、数量、场景）→ 操作 → 预期（可观察、可判定）；一条只验证一件事。
3. 标优先级：P0 核心循环 / 阻断错误 / 数据损坏；P1 体验 / 可读性 / 边缘优化。
4. 写回归检查表：每次构建必跑的 8~12 条，写最小闭环。
5. 补性能 / 日志：机型、FPS、同屏上限、卡顿；固定种子、日志字段、复现方式。
6. 执行记录：日期、版本、范围、结果；失败项链接到 Spec 规则 ID。
7. 自检：`check-docs.ps1`。

不要把：「看起来正常」当预期；一条用例验证多个系统；用实现细节代替玩家可观察结果。

## 4. 试玩

适用：灰盒第一次能完整跑一局；加入改变体验的内容后；里程碑评审前。

读取：`references/templates/07-checklists/checklists.md` 的「5 人试玩脚本」、`references/templates/06-playtests/0000-playtest-template.md`。

1. 准备：可运行构建、无阻断 bug；记录版本 / 种子 / 场景；至少 5 名试玩者；不提前讲解。
2. 观察前 3 分钟：多久知道操作？第一次死亡是否明白原因？第一次选择是否比较？是否主动重开？
3. 只问 3 个问题（见试玩脚本）。
4. 记录：`06-playtests/0001-日期-场景.md`；原话优先；记录观察，不辩护设计。
5. 提炼：3 条观察、3 条问题、3 条行动（对应 Spec / 验收 ID）。
6. 判断止损：5 人中 < 3 人想再来；说不出两局差异；不需要操作也能赢；选择只是数值；3 分钟内无紧张时刻——触发任意一条，先改循环，不加内容。

## 5. 变更与维护

适用：改已有行为 / 数值 / 状态 / UI；Spec 与实现不一致；新增系统但不想文档漂移。

1. 定位影响面：受影响的规则 ID 和 `AC-*` 验收 ID。
2. 先改 Spec：更新规则、公式、边缘情况，文末写变更记录。
3. 再改验收：行为变了但验收没变 = 没改完。
4. 判断是否要 ADR：方向、架构、存档、联机、付费、平台 → 新 ADR；纯数值 / UI 文案 → 不需要。
5. 自检：`check-docs.ps1`。
6. 验证：跑受影响的 P0 用例并记录结果。

完成标准：Spec / Acceptance / 变更记录三者一致；受影响的 P0 用例已跑；需要时已有新 ADR；检查通过。

不要把：只改代码不改文档；只改 Spec 不改验收；用「小改动」跳过变更记录；口头承诺不写行动项。
