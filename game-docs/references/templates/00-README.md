## 1. 文档分工

| 文档 | 回答什么问题 | 长度 | 谁维护 |
|---|---|---|---|
| [01 单局简报](01-run-brief.md) | 这一局是什么？为什么值得做？ | 1 页 | 设计 + 制作人 |
| [02 设计规范](02-design-spec.md) | 具体行为、公式、状态、边缘情况 | 长篇 | 设计 + 技术 |
| [03 验收矩阵](03-acceptance.md) | 怎么判定「做完了」 | 长篇 | QA + 设计 |
| [04 决策记录](04-adr/) | 为什么这么选，否决了什么 | 1~3 页/篇 | 决策人 |
| [05 评审记录](05-reviews/) | 谁认可、谁有条件、哪些行动项未关闭；试玩结论默认写这里 | 1~2 页/次 | 评审组织者 |
| [06 试玩记录（可选）](06-playtests/) | 试玩结果是否支持假设；不启用时并入 05 | 每次 1 页 | 你 + 观察者 |
| [07 检查清单](07-checklists/) | 什么时候算完成 | 1 页/份 | 制作人 + QA |

**一句话：**

- Run Brief = 假设
- Design Spec = 契约
- Acceptance = 证据标准
- ADR = 决策
- Review = 签字
- Playtest = 证据
- Checklist = 完成定义

> 如果项目不是 run-based（例如线性叙事、解谜），把 01 替换成「Vertical Slice Brief」，其余结构不变。

## 2. 状态标记

| 标记 | 含义 |
|---|---|
| `Draft` | 草案，允许大改 |
| `Proposed` | ADR 已提出，等待确认 |
| `Accepted` | 已确认，变更需新 ADR |
| `Conditional` | 有条件通过，行动项完成前不生效 |
| `Superseded` | 被新版本取代 |

## 3. 变更流程

任何行为变更，按顺序：

1. 改 `02-design-spec.md`，更新规则 ID
2. 改 `03-acceptance.md`，增加/修改验收用例
3. 在 Spec 文末写变更记录
4. 若涉及方向/架构，写新 ADR
5. 里程碑变更时，用 `review` skill 的 game profile 做一次评审并签字

**不允许：**

- 只改代码不改 Spec
- 只改 Spec 不改验收
- 在评审里口头承诺，不写进行动项
- 提前写未验证的内容

## 4. 评审

评审流程由 `review` skill 提供，游戏项目使用：

- `review/profiles/game.md`
- `review/templates/review.md`
- `review/templates/review-index.md`

**评审节奏：**

- M0：规范评审
- M1：灰盒评审
- M2：垂直切片评审
- 每次评审必须产出：签字表 + 行动项 + 结论
- active / archive 索引维护在 `05-reviews/README.md`

## 5. 写作原则

1. **只写当前里程碑。** 不提前写 8 分钟版本、Boss、多角色。
2. **规则要可判定。** 「手感好」不是规则；「40 敌人 60 FPS」是。
3. **一条规则一个 ID。** 便于验收、变更、追溯。
4. **文案写「做什么」，不写「感觉如何」。**
5. **没有决策价值的内容删掉。**
