# 游戏设计复用模式

> 这些是跨项目复用的**设计模式**，不是某个游戏的具体规则。每条只给判断规则和验收方向；数值、内容、题材由项目自己填。

## 1. 单局结构契约

**问题**：一局什么时候结束？玩家为什么赢/输？收尾有没有高潮？

**规则**：

- 一局只能有一个主要胜利条件；额外条件必须明确优先级。
- 收尾必须是设计过的事件（Boss、撤离、结算高峰），不能只是“时间到”。
- 多模式必须定义**平衡基准模式**，并明确各模式改变的是时长、密度还是难度；不要用模式名暗示未定义的含义。
- 失败必须可解释；不要用隐藏计时或不可见规则收尾。

**反模式**：5 分钟到了直接弹胜利；Quick 模式实际更密更长；Boss 只是血包。

**证据**：固定种子跑通“开局→收尾→胜负”；记录到达收尾的比例与收尾时长。

## 2. 决策密度与承诺

**问题**：玩家什么时候做出真正影响构筑的选择？

**规则**：

- 单局前 1/3 至少出现一次**承诺型选择**：改变后续卡池、路线、形态或规则，而不只是 +5% 数值。
- 承诺型选择要有代价或排他性；如果两个选项都能无损拿，它不是承诺。
- 后续卡池应体现倾向，但不要完全锁死；保留少量跨路线可能。
- 选择结果要可解释：玩家能说出“我为什么走这条路”。

**反模式**：前 10 级全是数值；进化条件只给一点加成、不影响路线；所有选项最终都能拿满。

**证据**：记录选择时间点、选择分布、重开时是否尝试另一条路线。

## 3. 威胁-成长匹配

**问题**：玩家变强后，威胁有没有同步变强？

**规则**：

- 敌人 HP、伤害、攻击频率、组合压力至少有一项随局内时间成长。
- 玩家防御/回复成长时，必须有对应的爆发伤害、破防、区域封锁或资源压力。
- 不要只看单点 TTK；看每分钟承伤、死亡时间分布、不同构筑的生存曲线。
- 允许某些构筑在特定维度强，但要有明确弱项和反制场景。

**反模式**：只加敌人血量；玩家护甲/屏障叠满后后段反而更安全；Boss 是唯一威胁。

**证据**：固定种子回归的承伤/分钟、死亡时间分布、TTK 分布、防御堆叠局与输出局的对比。

## 4. 空间-胜负耦合

**问题**：地图形态是否支持核心动词和胜利条件？

**规则**：

- 空间结构（固定竞技场、滚动大地图、房间制）必须和胜利条件、刷怪方式、节奏一起决策。
- 固定竞技场适合可控 Boss/弹幕/性能；大地图强化风筝与探索；房间制适合清怪与路线选择。
- 改变地图不是美术改动，会同时改变索敌、生成、拾取、Boss 场地和性能预算。
- 在切换前先测：贴边时间、平均最近敌人距离、冲刺使用率、承伤来源。

**反模式**：为了“像某游戏”换大地图，却没改刷怪和胜负；固定竞技场里只靠堆怪制造压力。

**证据**：空间指标 + 同内容在不同空间结构下的对照原型。

## 5. 变换契约

**问题**：内容进化/升级/合并后，旧投入怎么处理？

**规则**：

- 任何变换都要定义三类结果：直接继承、折算转换、失效。
- 失效必须显式告知玩家，不能静默吞掉。
- 转换公式要可读；UI 在变换前展示结果。
- 变换后重新计算属性，不保留旧形态的隐藏状态。

**反模式**：进化后旧天赋消失但不提示；转换公式只写在代码里；UI 只显示新武器不显示损失。

**证据**：变换前后的属性/卡池对比；UI 截图或文本检查；回归覆盖每条转换。

## 6. 证据阶梯

**问题**：这个结论是用什么证据得出的？

**规则**：

| 层 | 回答 | 不能回答 |
|---|---|---|
| 静态预览 / 数据模型 | 规则、数值、展示是否自洽 | 实际手感、压力 |
| 真实模拟 / 受控压测 | 机制能否跑通、性能是否达标 | 真人是否觉得好玩 |
| 固定种子 + bot 回归 | 可复现性、承伤/死亡分布 | 学习曲线、乐趣 |
| 真人试玩 | 理解、乐趣、重开意愿 | 大规模平衡 |

- 低层证据不能替代高层结论。
- 预测必须标注验证状态；不要用“模拟通过”证明“玩家喜欢”。

**反模式**：用静态图鉴证明武器好玩；用 bot 胜率证明真人体验；用 5 人试玩证明大样本平衡。

**证据**：每层结论标注来源、样本量、日期。

## 7. 可归因失败

**问题**：玩家死了，能不能说清为什么？

**规则**：

- 每局记录：种子、构筑、关键选择、承伤/分钟、承伤来源、死亡时间、Boss 状态。
- 死亡原因必须来自实际伤害来源，不能写死。
- 不能归因时先补观测，不凭感觉调数值。
- 失败要能区分：输出不够、防御不够、走位失误、构筑被克制、内容不理解。

**反模式**：只记录“死了”；死因永远是同一个敌人；没有承伤分布。

**证据**：回归 JSON / 日志字段；死亡时间分布；按来源的承伤表。

## 8. 表现-规则分离

**问题**：UI 是否知道太多具体内容？

**规则**：

- 表现层只消费能力描述、只读 ViewModel 或预览模型，不判断具体武器/角色/技能类型。
- 静态预览不伪造战斗公式；动态试炼/模拟复用真实系统。
- 内容新增只扩展能力描述，不改 UI 分支。
- 预览和真实模拟是两层：预览回答“是什么”，模拟回答“实际多强”。

**反模式**：`if weapon.id == ...`；图鉴自己重算 DPS；试炼场另写一套伤害公式。

**证据**：UI 代码无具体 ID/类型分支；预览与真实模拟的同配置偏差在阈值内。

## 怎么用

1. 新项目先过 1、2、4：单局结构、决策密度、空间形态。
2. 有成长/进化后过 3、5：威胁匹配、变换契约。
3. 做预览/试炼/平衡时过 6、8：证据阶梯、表现分离。
4. 每次试玩或调参后过 7：失败是否可归因。
