# 游戏设计复用模式

> 这些是跨项目复用的**设计模式**，不是某个游戏的具体规则。每条只给判断规则和验收方向；数值、内容、题材由项目自己填。

## 1. 单局结构规则

**问题**：一局什么时候结束？玩家为什么赢/输？收尾有没有高潮？

**规则**：

- 一局只能有一个主要胜利条件；额外条件必须明确优先级。
- 收尾必须是设计过的事件（如收尾战、撤离、结算高峰），不能只是“时间到”。
- 多模式必须定义**平衡基准模式**，并明确各模式改变的是时长、密度还是难度；不要用模式名暗示未定义的含义。
- 失败必须可解释；不要用隐藏计时或不可见规则收尾。

**反模式**：时间到直接弹胜利；模式名与实际变更不符；收尾只是血量墙。

**证据**：固定种子跑通“开局→收尾→胜负”；记录到达收尾的比例与收尾时长。

## 2. 决策密度与承诺

**问题**：玩家什么时候做出真正影响构筑的选择？

**规则**：

- 单局前 1/3 至少出现一次**承诺型选择**：改变后续可选内容、路线、形态或规则，而不只是小幅数值。
- 承诺型选择要有代价或排他性；如果两个选项都能无损拿，它不是承诺。
- 后续可选内容应体现倾向，但不要完全锁死；保留少量跨路线可能。
- 选择结果要可解释：玩家能说出“我为什么走这条路”。

**反模式**：前若干等级全是数值；成长条件只给一点加成、不影响路线；所有选项最终都能拿满。

**证据**：记录选择时间点、选择分布、重开时是否尝试另一条路线。

## 3. 威胁-成长匹配

**问题**：玩家变强后，威胁有没有同步变强？

**规则**：

- 威胁的耐久、伤害、频率、组合压力至少有一项随局内时间成长。
- 玩家防御/回复成长时，必须有对应的爆发伤害、破防、区域封锁或资源压力。
- 不要只看单点击杀时间；看压力/分钟、失败时间分布、不同构筑的生存曲线。
- 允许某些构筑在特定维度强，但要有明确弱项和反制场景。

**反模式**：只加威胁耐久；玩家防御叠满后后段反而更安全；只有一个收尾威胁。

**证据**：固定种子回归的压力/分钟、失败时间分布、击杀时间分布、防御堆叠局与输出局的对比。

## 4. 空间-胜负耦合

**问题**：地图形态是否支持核心动词和胜利条件？

**规则**：

- 空间结构（固定空间、滚动地图、房间制）必须和胜利条件、生成方式、节奏一起决策。
- 固定空间适合可控的收尾战/弹幕/性能；大地图强化风筝与探索；房间制适合清怪与路线选择。
- 改变地图不是美术改动，会同时改变索敌、生成、拾取、收尾战场地和性能预算。
- 在切换前先测：边界停留、平均最近威胁距离、机动使用率、压力来源。

**反模式**：为了“像某游戏”换大地图，却没改生成和胜负；固定空间里只靠堆压力单位制造压力。

**证据**：空间指标 + 同内容在不同空间结构下的对照原型。

## 5. 变换规则

**问题**：内容进化/升级/合并后，旧投入怎么处理？

**规则**：

- 任何变换都要定义三类结果：直接继承、折算转换、失效。
- 失效必须显式告知玩家，不能静默吞掉。
- 转换公式要可读；UI 在变换前展示结果。
- 变换后重新计算属性，不保留旧形态的隐藏状态。

**反模式**：变换后旧能力消失但不提示；转换公式只写在代码里；UI 只显示新形态不显示损失。

**证据**：变换前后的属性/可选内容对比；UI 截图或文本检查；回归覆盖每条转换。

## 6. 证据阶梯

**问题**：这个结论是用什么证据得出的？

**规则**：

| 层 | 回答 | 不能回答 |
|---|---|---|
| 静态预览 / 数据模型 | 规则、数值、展示是否自洽 | 实际手感、压力 |
| 真实模拟 / 受控压测 | 机制能否跑通、性能是否达标 | 真人是否觉得好玩 |
| 固定种子 + bot 回归 | 可复现性、压力/失败分布 | 学习曲线、乐趣 |
| 真人试玩 | 理解、乐趣、重开意愿 | 大规模平衡 |

- 低层证据不能替代高层结论。
- 预测必须标注验证状态；不要用“模拟通过”证明“玩家喜欢”。

**反模式**：用静态预览证明内容好玩；用 bot 胜率证明真人体验；用少量试玩证明大样本平衡。

**证据**：每层结论标注来源、样本量、日期。

## 7. 可归因失败

**问题**：玩家死了，能不能说清为什么？

**规则**：

- 每局记录：种子、构筑、关键选择、压力/分钟、压力来源、失败时间、关键阶段状态。
- 失败原因必须来自实际压力来源，不能写死。
- 不能归因时先补观测，不凭感觉调数值。
- 失败要能区分：输出不够、防御不够、操作失误、构筑被克制、内容不理解。

**反模式**：只记录“失败”；失败原因永远是同一个；没有压力分布。

**证据**：回归 JSON / 日志字段；失败时间分布；按来源的压力表。

## 8. 表现-规则分离

**问题**：UI 是否知道太多具体内容？

**规则**：

- 表现层只消费能力描述、只读 ViewModel 或预览模型，不判断具体内容类型（如武器/角色/技能）。
- 静态预览不伪造核心公式；动态模拟复用真实系统。
- 内容新增只扩展能力描述，不改 UI 分支。
- 预览和真实模拟是两层：预览回答“是什么”，模拟回答“实际多强”。

**反模式**：UI 按具体内容 ID/类型分支；预览自己重算公式；模拟另写一套核心公式。

**证据**：UI 代码无具体 ID/类型分支；预览与真实模拟的同配置偏差在阈值内。

## 9. 平衡基准值与重定

**问题**：这次调参/改规则后，旧平衡结论还能用吗？

**规则**：

- 每个模式定义**平衡基准模式**和独立的平衡预算；不要让难度档同时改选取次数、经验、密度等多个维度而不留归因。
- 用多种子 + 多玩家模型看分布，不只看单局或平均值；至少记录 P50，必要时记录 P90/失败时间。
- 模型（bot/kiter/greedy 等）是观察工具，不是真人替代；模型结论只能回答「机制是否跑通/压力是否异常」，不能回答「好不好玩」。
- 行为变化（选取次数、掉落、数值曲线）会使旧基准值失效；旧值标作废，按相同样本设计重跑后回填。
- 样本不足时显式 `SKIP`，不能静默 PASS；检查阈值变更要记录原因与样本。
- 先判断是实现错误、测试错误还是设计变化，再决定调数值还是改阈值。

**反模式**：用旧基准值证明新版本通过；只跑一个种子；只报平均等级；为了通过检查放宽阈值；把 bot 胜率当真人体验。

**证据**：固定种子的分布表（P50/P90）、失败时间、关键阶段指标、命令与提交、旧基准值作废说明。

## 10. 错误预防与恢复

**问题**：玩家会不会因为看不见的规则，进入不可逆的坏状态？

**规则**：

- 把错误处理分成三层：**预防**（不让错误发生）→ **缓解**（发生后可撤回/确认）→ **恢复**（坏状态有出口）。
- 非法动作应被**前置校验**：按钮置灰、结果预览、约束提示；不要让玩家先执行再失败。
- 危险结果必须 **telegraph**：操作前能看见后果，操作后能看见原因。
- 检查 **soft-lock / deadlock**：每个“资源耗尽/空间满/无可行动”状态都要有出口（回收、重置、复活、结算）。
- 死资源（不能使用、不能消耗、没有 sink）是设计缺陷，不是“硬核”。

**反模式**：只有惩罚没有恢复；错误延迟到很久以后才爆发；把“玩家自己避免”当成规则说明。

**证据**：失败路径表；每个不可逆操作的前置提示；从坏状态恢复的测试。

## 11. 资源经济：来源、消耗、回收

**问题**：每种资源有没有来源和 sink？会不会只进不出？

**规则**：

- 为每种关键资源画 **faucet / sink 表**：来源、消耗、回收、上限、枯竭风险。
- 空间、行动次数、货币、时间、耐心、清理次数都算资源。
- 只进不出的资源最终一定堵死；只出不进的资源会让玩家不敢用。
- 回收机制要**可见、可预期、有冷却/成本**，不能靠隐藏随机。
- 资源压力应来自“选择和代价”，不是来自“死资源越积越多”。

**反模式**：大量不可用道具占满背包；清理次数固定且不可恢复；资源满了只能等惩罚。

**证据**：资源表；一局内的来源/消耗曲线；枯竭与堵塞测试。

## 12. 随机性契约

**问题**：随机是公平的、可解释的、可复现的吗？

**规则**：

- 写清随机源：种子、洗牌、权重、保底、重掷、可见范围。
- 纯随机不等于公平；需要 **防旱、防堵、可达性、连胜/连败** 等软约束。
- 内容生成应有最低保证：目标可达、必要资源可获取、不会连续出现不可用组合。
- 随机结果要能解释：玩家能说“为什么这局难/为什么我能过”，而不是“运气”。
- 固定种子必须能复现同一序列；随机不能替代难度设计。

**反模式**：完全无约束随机；隐藏保底；用随机波动掩盖经济/难度问题；不同端结果不可复现。

**证据**：生成规则表；固定种子回归；干旱/堵塞/无解统计；随机种子分布。

## 13. 构筑因子的阶段

**问题**：构筑（build）什么时候设计、什么时候实现？

**规则**：

- **构筑因子属于 pre-production / 系统设计阶段**：在核心 loop 验证后、内容生产前，定选择时机、对象、代价、协同、内容预算与平衡基线。
- 不要把构筑当成“后期加系统”：它会改变生成、经济、内容、UI 和解锁。
- 先验证 **一条构筑轴**（run-start / in-run / between-run 之一），再扩因子；不要先做 50 个内容。
- 选择应有承诺性：排他、代价、改变后续可选内容；无代价的加成不是构筑。
- 构筑不能救一个不好玩的核心 loop；先验证 loop，再做构筑。

**反模式**：先生产大量卡/升级再找构筑；所有选择都能无损拿满；构筑只加数值；把构筑当作核心问题的遮羞布。

**证据**：构筑轴表；一条轴的灰盒/垂直切片；使用率、重开路线、支配策略检查。

## 怎么用

1. 新项目先过 1、2、4：单局结构、决策密度、空间形态。
2. 有成长/进化后过 3、5：威胁匹配、变换规则。
3. 做预览/试炼/平衡时过 6、8：证据阶梯、表现分离。
4. 每次试玩或调参后过 7、9：失败是否可归因、基准值是否需重定。
5. 新规则/新资源/新随机/新构筑时过 10~13：防错恢复、资源 sink、随机性契约、构筑阶段。
