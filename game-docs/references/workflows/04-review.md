# Workflow 04 — 6 人面板评审

## 何时使用

- 当前里程碑的 Spec / Acceptance 完成，准备进入实现或下一阶段
- 需要正式签字、条件和行动项
- 方向有争议，需要多视角压力测试

## 读取

- `references/templates/05-reviews/0000-review-template.md`
- `references/templates/07-checklists/doc-review.md`
- 目标项目的 `02-design-spec.md`、`03-acceptance.md`

## 步骤

1. **先自检**
   - 按 `doc-review.md` 检查结构、内容、一致性、范围。
   - 如果环境里有 `docs-audit` skill，可额外跑一遍文档集审核；没有就用本清单。
   - 自检不通过，先修文档，不要开评审。

2. **准备评审材料**
   - 明确评审对象、版本、范围。
   - 列出本次必须决定的问题。
   - 不要把未完成的内容混进来。

3. **跑 6 个角色**
   - 目标玩家：是否易懂、是否想再来
   - 游戏设计师：循环、选择、节奏
   - 技术负责人：可行性、性能、维护
   - 美术/UX：可读性、表现成本
   - 制作人：范围、时间、砍线
   - QA：可测试性、边界
   - 每个角色必须给出：认可 / 条件 / 否决理由。

4. **写签字表**
   - 结论只能是：通过 / 有条件通过 / 否决。
   - 条件必须可执行、有截止时间。

5. **写行动项**
   - 每条行动有 ID、写入位置、截止。
   - 行动项关闭前，不得进入下一阶段。

6. **更新状态**
   - 更新目标项目 `00-README.md` 的当前状态。
   - 若评审改变了方向/架构，写新 ADR，旧 ADR 标 `Superseded`。

7. **自检**

   ```powershell
   .\scripts\check-docs.ps1 -DocsPath "<target>\docs"
   ```

## 完成标准

- 6 个角色都有意见
- 签字表完整
- 行动项可执行、有截止
- 结论明确
- 文档状态已更新
- 检查通过

## 不要把

- 把「大家觉得不错」当评审结论
- 只写认可，不写条件
- 评审后不写行动项
- 让未关闭的条件进入下一阶段
