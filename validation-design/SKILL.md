# 验证阶段设计

目标：让验证阶段回答**模型问题**，而不是只回答“能不能跑”。

验证阶段最常见的失败不是实现跑不起来，而是：

- 只证明可行性；
- 没有失败判据；
- 证据层级不够；
- 结论超出了测试范围。

本 skill 负责把验证计划写成可执行、可失败、可解释的形式；不负责写完整 Spec 或验收矩阵（那是 `game-docs`）。

## 何时使用

- 设计一个验证阶段、原型、实验或里程碑验证
- 审计现有验证计划：它到底证明了什么
- 判断现有证据能否支持“模型成立”的结论
- 设计反事实、消融、对照或失败判据
- 决定什么时候从静态/模拟证据升级到真人试玩

不适用：

- 完整 GDD / Spec / 验收矩阵 → `game-docs`
- 代码审查 / 合并前检查 → `code-review`
- 文档集交叉引用审核 → `docs-audit`
- 验收状态跟踪 → `implementation-track`
- 纯外部调研 → `topic-research`

## 行为

无主动打断。用户要求设计或审计验证阶段时使用；不主动评价日常实现细节。

## 核心规则

1. **先写模型假设。** 不是“做出来看看”，而是“如果模型成立，应该观察到什么行为”。
2. **写明竞争解释。** 什么更简单的模型也能通过这个测试？如果通过不能区分两者，测试不够。
3. **变量与控制分离。** 这一轮改什么、什么保持不变；不要同时改频率、伤害、HP、克制后再说“感觉对了”。
4. **指标可观察。** 时间、次数、胜率、剩余资源、选择分布、失败原因；不写“手感好”。
5. **失败判据先于结果。** 什么结果会证明模型错了？没有失败判据的测试只是演示。
6. **反事实/消融。** 去掉一个机制后结果是否变化？不变，机制可能只是装饰。
7. **证据层级匹配结论。** 静态预览只能证明可读性；模拟只能证明规则内行为；真人试玩才能证明决策/体验。不要用低层证据替代高层结论。
8. **范围声明。** 明确“本阶段不能证明什么”。1v1 参数验证不能替代 2v2/地形/决策验证。
9. **决策规则。** 通过 / 迭代 / 停止；通过后下一步是什么，失败后改哪个变量。
10. **记录反例。** 失败结果和意外结果比成功截图更有价值。

## 审计清单

对现有验证计划逐项问：

- [ ] 验证问题是不是“模型是否产生 X”，而不是“功能能不能跑”？
- [ ] 有没有一个结果会让计划失败？
- [ ] 测试能否区分目标模型和更简单的替代模型？
- [ ] 变量是否隔离？有没有同时改多个东西？
- [ ] 指标是否可观察、可复现？
- [ ] 有没有反事实/消融/对照？
- [ ] 证据层级是否匹配结论？
- [ ] 结论是否超出了测试范围？
- [ ] 有没有调参/迭代回路？
- [ ] 通过/失败后分别改什么？

## 输出

- 验证计划：用 `templates/validation-plan.md`
- 审计报告：按“发现 / 严重度 / 证据 / 行动项”输出；发现优先于修改
- 游戏机制验证：读 `references/game-mechanics.md`；战斗模型细节交给 `game-combat-model`

## 反模式

- “先做出来看看”——没有假设、没有失败判据
- “能跑通就算验证通过”
- 只截成功画面，不记录失败/边界
- 一次成功 sim 就宣布模型成立
- 用 1v1 自动对砍证明 2v2 决策成立
- 用静态预览证明手感
- 同时改频率、伤害、HP、克制，无法归因
- 把“玩家没看出来”归因于表现，而不检查模型是否真的不同

## 交接

- 设计模型：`design-stage`；游戏战斗模型：`game-combat-model`
- 写 Spec/验收：`game-docs`
- 多角色评审：`review`
- 跟踪行动项/状态：`implementation-track`
- 结果分类与回流：`feedback-stage`

## 边界

- 不写项目具体数值；数值属于项目文档
- 不替代 `game-docs` 的验收矩阵
- 不替用户拍板“通过/不通过”；给出证据与条件
- 审计报告先输出发现，再改文件
