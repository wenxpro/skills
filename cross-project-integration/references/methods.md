# 方法背景

> 本文件只给方法来源与使用场景，不写项目细节。团队偏好放 `standards.md`。

## 1. 模块化与信息隐藏

Parnas 的信息隐藏：模块按“最可能变化的知识”拆分，而不是按执行步骤拆分。

用法：

- 先找易变点：格式、协议、策略、外部依赖、数据来源。
- 把易变点藏在接口后面。
- 跨项目只暴露稳定接口，不暴露内部类型。

对应检查：

- 上游是否暴露了内部对象？
- 下游是否直接改了上游字段？
- 变化是否只影响一个模块？

## 2. 约定式设计（Design by Contract）

每个接口写清：

- 前置条件：调用方必须提供什么。
- 后置条件：返回什么、保证什么。
- 不变量：什么永远不能变。
- 错误语义：失败时谁重试、谁降级、谁记录。

用法：

- 跨项目接口必须写前置/后置/错误语义，不能只有字段名。
- 生产者和消费者各写一份检查。
- 失败路径和正常路径同等重要。

## 3. 依赖倒置与稳定依赖

- 稳定的一方定义接口，易变的一方实现适配。
- 上游不依赖下游内部；下游通过适配层依赖上游发布接口。
- 依赖方向必须无环。

检查：

- 是否出现上游 import 下游？
- 是否出现双向依赖？
- 共享类型是否放在中立位置？

## 4. 发布语言与适配层

跨项目通信优先使用发布语言（协议、schema、消息、报告字段），不要共享内部对象。

适配层职责：

- 翻译字段与错误码。
- 做语义校验。
- 隔离版本差异。
- 不把上游字段直接塞进下游领域对象。

关系类型：

| 关系 | 适用 |
|---|---|
| 发布语言 | 跨项目接口稳定、需要独立演进 |
| 适配层 | 两边模型不同、需要翻译 |
| 共享内核 | 少量稳定类型，双方共同维护 |
| 独立演进 | 没有强依赖，各自定义 |

## 5. DSM 与 N²

DSM（依赖矩阵）：

- 行依赖列；找共享热点、循环、并行边界。
- 用重排暴露块结构。
- 元素 8~20 个，不要按文件列几百行。

N²（接口图）：

- N 个子系统放成 N×N 方阵。
- 对角线是子系统，非对角线写输入/输出。
- 用于把每个跨项目接口的字段、方向、owner 写清。

顺序：先用 DSM 找热点，再用 N² 写接口内容。

## 6. 组织与认知边界

Conway 定律：系统结构会复制组织沟通结构。

Team Topologies 的四个类型可作为映射参考：

- Stream-aligned：按业务流负责。
- Platform：提供共用能力。
- Enabling：提供方法与工具。
- Complicated-subsystem：需要专门能力的子系统。

用法：

- 先定 owner 和写集，再谈并行。
- 共享文件多、沟通路径多，说明边界没拆好。
- 不要让一个工作流同时承担平台和业务交付。

## 7. 发布工程

- 版本：接口版本与产品版本分开；不兼容变化明确标注。
- 消费者驱动检查：消费者定义期望，生产者验证兼容。
- 迁移：新旧并行、feature flag、灰度、回滚条件。
- 切换：默认路径切换晚于 parity 通过。
- 证据：固定输入、命令、输出、差异说明。

## 8. Agent / 多执行者协作

把执行者当“有界工作进程”，不是线程：

- 每个执行者有任务、写集、完成标准、证据。
- 执行者不共享完整上下文，靠工件和接口登记表协作。
- 主执行者/集成 owner 负责分解、调度、集成、验收。
- 失败隔离：独立工作区、独立检查、独立回滚。
- 监督树：执行者失败只重启该执行者，不拖垮全局。

## 9. Lean / 流与并行度

- 并行不是越多越好；共享文件越多，集成成本越高。
- 限制同时进行的工作流数量。
- 固定集成节奏，例如每周一次集成窗口。
- 观察：前置时间、集成频率、变更失败率、返工次数。

## 10. 选择方法

| 问题 | 先用 |
|---|---|
| 模块边界不清 | 信息隐藏、依赖倒置 |
| 接口字段/错误不清 | 约定式设计、N² |
| 不知道谁能并行 | DSM、写集 |
| 上下游关系不清 | 发布语言、适配层 |
| 发布节奏冲突 | 版本、集成窗口、feature flag |
| 多执行者冲突 | 写集、单一写者、监督树 |
| 共享文件冲突 | 冻结点、集成 owner |
