# 跨项目协作设计

目标：多个项目/仓库共同交付一项能力时，让边界、接口、顺序、验证和交接都能被检查，而不是靠“大家同步一下”。

> 通用规则在本文件；团队偏好在 [standards.md](standards.md)；方法背景在 [references/methods.md](references/methods.md)；模板在 [templates/](templates/)。

## 何时使用

- 一项能力跨两个以上仓库、团队或发布节奏。
- 需要定义上下游、接口登记、兼容版本或迁移步骤。
- 需要判断哪些工作流能并行、哪些必须先冻结。
- 需要跨项目交接、合并顺序或切换/回滚方案。
- 多代理/多会话并行执行，但共享接口或共享文件。

不适用：

- 单仓库模块边界与依赖方向 → `responsibility-design`
- 单项目里程碑与工作包排期 → `roadmap-planning`
- 多个仓库的提交与推送 → `multi-repo-commit`
- 单次会话的交接与恢复 → `session-handoff`
- 模型/供应商接入与失败降级 → `llm-integration`
- 产品范围、取舍与验收决策 → `review` / `design-stage`

## 核心原则

1. **一个能力一张接口登记表**：一个 owner、一个版本、一组检查；不维护两份。
2. **上下游分离**：上游发布接口，下游用适配层翻译；不共享内部类型和内部状态。
3. **先冻结再并行**：没有冻结点、没有写集划分的并行是假并行。
4. **生产者和消费者都检查**：字段、错误语义、兼容版本、失败路径分别验。
5. **迁移不一次切换**：新旧并行 + parity/feature flag + 明确回滚条件。
6. **共享文件有单一写者**：共享文件/资源要么冻结，要么指定唯一写者。
7. **证据优先**：固定输入、命令、输出、差异说明；不靠“看起来对”。
8. **主执行者/集成 owner 只做调度、集成、验收**：子任务由执行者负责，不把全局决策下放给执行者。

## 操作顺序

1. 判断是否触发
2. 画上下游
3. 建接口登记表
4. 建依赖矩阵
5. 写集成计划
6. 验证
7. 交接与回滚
8. 收口与复盘

### 第一步：判断是否触发

先回答四个问题：

| 问题 | 如果“是” |
|---|---|
| 是否两个以上仓库/团队共同交付一项能力？ | 需要跨项目设计 |
| 是否共享接口、数据格式、错误语义或报告字段？ | 需要接口登记表 |
| 是否要并行推进多个工作流？ | 需要依赖矩阵、写集与冻结点 |
| 是否需要迁移、替换或新旧并存？ | 需要集成计划、parity、回滚 |

四个都为“否”，不要用本 skill；用 `responsibility-design` 或 `roadmap-planning`。

### 第二步：画上下游

至少写清：

- 上游：谁生产接口、谁决定版本、谁负责兼容。
- 下游：谁消费接口、谁做适配、谁做最终裁决。
- 关系类型：发布语言、适配层、共享内核、独立演进。
- 边界：哪些字段/状态只在内部，哪些允许跨项目。

输出一张简图或表，不要求正式 UML：

```text
上游（生产者） → 发布接口 → 下游适配层 → 下游领域
```

适配层负责翻译，不把上游字段直接塞进下游领域对象。

### 第三步：建接口登记表

用 [接口登记表](templates/interface-register.md)。每个接口一行，至少包含：

- 接口/消息名、生产者、消费者；
- 版本与兼容范围；
- 输入、输出、错误语义；
- owner、冻结点；
- 生产者检查、消费者检查；
- 状态（草案/冻结/弃用）。

规则：

- 一个接口只有一个 owner。
- 版本变化必须写兼容说明；不兼容变化标为破坏性变更。
- 错误语义必须写清：谁重试、谁降级、谁记录。
- 字段差异要分类：格式差异、语义差异、版本差异；不要一律当 bug。

### 第四步：建依赖矩阵

用 [依赖矩阵](templates/dependency-matrix.md)，同时做两张：

1. **DSM（依赖矩阵）**：谁依赖谁，找共享热点、循环、并行边界。
2. **N²（接口图）**：每个跨项目接口传什么、谁生产、谁消费。

DSM 约定：

- 行依赖列；保持一致。
- `X` = 强依赖，`S` = 共享文件/资源，`W` = 弱依赖。
- 重排行列，找块、找循环、找热点。
- 元素控制在 8~20 个；不要按文件列几百行。

读图规则：

- 密集列 = 共享热点，先冻结。
- 循环 = 先拆接口或先做决策，不要硬并行。
- 空行/空列 = 可并行。
- 块 = 适合作为一个工作包或模块。

### 第五步：写集成计划

用 [集成计划](templates/integration-plan.md)。至少包含：

- 工作流、owner、写集、读集；
- 共享文件/资源与冻结窗口；
- 合并顺序与依赖；
- 集成检查（生产者、消费者、端到端）；
- 切换方式与回滚条件；
- 未决问题与 owner。

规则：

- 写集重叠的工作流不能同时写；要么拆，要么冻结，要么指定唯一写者。
- 先做上游接口，再做下游适配，最后做端到端。
- 集成检查不是“全量测试通过”就够；必须有接口级检查。
- 新旧路径并存时，默认路径切换必须晚于 parity 通过。

### 第六步：验证

至少三层：

| 层 | 检查 |
|---|---|
| 生产者 | 接口格式、版本、错误码、边界值 |
| 消费者 | 解析、语义校验、失败降级、重复/迟到消息 |
| 端到端 | 固定输入、固定 seed、parity、回放、切换/回滚 |

证据包：

- 固定输入/样本；
- 运行命令；
- 输出报告/日志；
- 与预期的差异说明；
- 执行日期与版本。

### 第七步：交接与回滚

跨项目交接用 [跨项目交接](templates/cross-repo-handoff.md)，必须带：

- 每个仓库的分支、HEAD、工作区状态；
- 接口版本与冻结状态；
- 已完成/未完成；
- 验证证据位置；
- 下一步第一条命令；
- 回滚方式与触发条件。

### 第八步：收口与复盘

- 更新接口登记表状态；
- 旧路径标记弃用或删除计划；
- 记录本次集成的差异与原因；
- 把新增的共享文件/热点补进依赖矩阵；
- 未关闭项写 owner 与下一次检查点。

## 边界

- 本 skill 不决定产品范围、优先级或验收取舍；回 `review` / `design-stage`。
- 不替代单项目模块设计；模块内部边界用 `responsibility-design`。
- 不替代单项目排期；里程碑与工作包用 `roadmap-planning`。
- 不替代提交编排；多仓库提交用 `multi-repo-commit`。
- 不替代会话交接；单次会话切换用 `session-handoff`。
- 不强制所有项目都上重流程；只有跨项目、共享接口、需要并行或迁移时才用。

## 反模式

- 只建共享文档，不写 owner、版本、冻结点。
- 两个工作流同时改同一文件，靠“合并时再看”。
- 用全量测试代替接口检查。
- 把格式差异、语义差异、版本差异混为一谈。
- 新旧路径没有 parity 就切默认。
- 主代理把所有细节抓在手里，子代理没有写集和完成标准。
- 子代理自行决定跨项目取舍，没有集成 owner。
- 依赖矩阵画完不排期、不定 owner、不加检查。

## 交接

| Skill | 关系 |
|---|---|
| `design-stage` | 设计阶段判断是否需要跨项目协作 |
| `responsibility-design` | 单项目上下文、模块所有权、依赖方向 |
| `roadmap-planning` | 跨项目工作流进入里程碑与工作包 |
| `delivery-stage` | 集成计划进入交付与合并前检查 |
| `multi-repo-commit` | 按仓库提交、推送与部分失败处理 |
| `session-handoff` | 跨项目会话边界与工作记忆 |
| `llm-integration` | 模型接入、失败降级、回放与选型 |
| `docs-core` / `docs-audit` | 接口登记与项目文档的单一事实源 |
