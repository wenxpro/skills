# 反馈阶段

目标：让结果变成下一步决策，而不是停在“测试完了 / 试玩完了”。

## 入口

有结果需要解释和回流时进入：测试、试玩、发布、代码审查、文档审计、验收状态更新之后。

开始前确认：

1. 证据可复核，带日期、版本、样本、命令（按适用）
2. 能区分事实、判断和推断
3. 知道反馈对象：设计、规划还是修复

不适用：当前设计 → `design-stage`；实现与提交 → `delivery-stage`；代码审查本身 → `code-review`。

## 处理

1. 收集证据，标明来源与适用范围
2. 分类：通过 / 失败 / 偏差 / 过时 / 需要决策
3. `implementation-track` 更新验收状态与偏差
4. 文档漂移交 `docs-audit` / `docs-core` 修正
5. 设计、范围、取舍变化交 `review`，不直接改设计结论
6. 版本、优先级、下一期交 `roadmap-planning`
7. 需要重新设计交 `design-stage`；需要修复交 `delivery-stage`

## 证据规则

- 历史证据保留当时结论，不追改；当前状态用最新实测。
- 失败、跳过、样本不足都记录，不隐藏。
- 单次样本不外推长期结论；标注样本量与适用范围。
- 结论要能指向日志、测试、文档或提交。

## 出口

反馈结束至少留下：

1. 证据范围与来源
2. 通过 / 失败 / 偏差 / 过时清单
3. 验收状态更新
4. 文档修正或待修正项
5. 待评审决策与回流项
6. 未关闭项与 owner

## 反模式

- 借反馈直接改设计结论。
- 只报通过项，隐藏失败、跳过或样本不足。
- 用单次样本证明长期趋势。
- 反馈开成状态会议，没有决策或行动。
- 行动项没有 owner 或下一步。

## 交接

- 上一阶段：`delivery-stage`
- 下一阶段：`design-stage` / `roadmap-planning` / `delivery-stage`
