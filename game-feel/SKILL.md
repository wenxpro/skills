# 游戏打击与反馈

目标：让玩家**看得懂、打得到、记得住**，而不是把所有反馈一起开到最大。

本 skill 负责 contact 帧之后的反馈层：hitstop、震屏、闪白、trail、音效、震动、时间缩放。攻击时间轴与数值用 `game-combat-model`，动画资产/状态机用 `game-animation-rig`，UI 视觉用 `ui-baseline`。

## 何时使用

- 设计/审计轻击、重击、格挡/弹反、破防、处决、特殊交互的反馈
- 命中感弱、反馈糊、看不清起手、音效吵、震屏晕
- 需要给不同武器/角色做反馈差异，但不能改判定
- 需要固定步长验证 contact 帧与反馈时序

不适用：

- 伤害公式、TTK、攻击时间轴、克制预算 → `game-combat-model`
- 资产重定向、脚底接触、AnimationTree → `game-animation-rig`
- UI 布局、字号、无障碍 → `ui-baseline`
- 引擎音频总线/CLI/持久化 → `godot-game-runtime`

## 行为

参考型 skill，无主动打断。用户要求设计/审计打击感时使用。

## 核心规则

### 1. 反馈服从规则，不改变规则

- 命中帧、伤害、架势由战斗模型/动画接触事件决定。
- hitstop 冻结表现与位移，但不能改变伤害结算帧或输入窗口。
- 反馈延迟不能掩盖 contact 帧；所有反馈以 contact 为时间原点。
- 反馈可以放大差异，但不能让轻击看起来比重击更重。

### 2. 反馈分层，每层只做一件事

| 层 | 职责 | 不该做 |
|---|---|---|
| 起手/预告 | 让玩家识别攻击类型与时机 | 提前扣血、遮挡剪影 |
| 接触瞬间 | 证明「打到了」 | 改变伤害/判定 |
| 冲击 | 重量、方向、节奏 | 连续叠满、抢走可读性 |
| 收招/余波 | 给呼吸与下一次判断 | 拖到看不清下一次起手 |

每层只选一个主信号；其他层做辅助。

### 3. 预算先于堆料

- 每个事件定义：hitstop 时长、震屏幅度/频率/衰减、闪白帧数、trail 长度、音效/震动层级。
- 预算写进项目规范；本 skill 不写具体数值。
- 同类事件预算一致；不同重量可以分档，但不能「越重越全开」。
- 连续命中要限流；避免音效/震动/闪白叠加成噪音。
- 反馈强度要服务可读性，不是服务刺激。

### 4. 可读性优先

- 起手颜色/动作/音效/剪影至少两路可区分；颜色不能是唯一信息。
- 反馈不能遮住武器轨迹、起手颜色、Boss 姿态或双方位置。
- 闪白/震屏/刀光不能覆盖 UI 关键信息。
- 灰度/关声音下仍能识别攻击类型。
- 强反馈要给玩家恢复窗口；不能连续打断判断。

### 5. contact 对齐与固定步长

- 伤害/防御在 contact 事件结算；反馈也以 contact 为锚点。动画接触事件由 `game-animation-rig` 实现；本 skill 定义反馈预算与验证。
- 用固定步长审计：实际 contact 帧 vs 期望帧，记录差值。
- 动画过渡/混合可能吞掉首尾帧；反馈层不能假设动画一定到位。
- 视觉接触（剑刃/武器）与规则接触分别验证：前者用定格/录屏，后者用断言。

### 6. 重量与武器差异

- 轻/重/防御/破防/处决/特殊交互各自有可区分的反馈档位。
- 武器差异可以通过轨迹、音色、震动、hitstop 微调表达；不能改判定窗口。
- 同一事件在不同角色上保持一致语义；Boss 可以更重，但不能无预警秒杀。
- 弹反/破防/处决的反馈优先级高于普通命中；同时发生只保留最高优先级主信号。

### 7. 镜头与震动

- 震屏只改表现，不改看向点/锁定构图/输入方向。
- 幅度、频率、衰减、恢复时间写进项目规范；避免持续高频。
- 提供强度/关闭选项；不要让震动成为唯一命中信息。
- 镜头推近/拉远不能裁掉双方或遮挡起手。

### 8. 音效与震动

- 起手音、挥砍音、命中音、弹反音、格挡音、破防音、处决音、胜负音各自可辨。
- 音效不替代视觉；音量/静音可调；headless 不创建音频。
- 手柄震动分层，但要有上限/冷却；不要连续满强度。
- 音频/震动与画面同步在 contact 帧，不提前/延后。

### 9. 证据与主观边界

- 固定步长断言证明时序；高帧率录屏证明视觉接触；真人试玩证明「手感」。
- 静态截图不能证明 hitstop/震屏/音效。
- 结论要写清：证明了时序、可读性还是主观体验。
- 不同玩家对震动/闪白敏感度不同；可访问性选项是基线。

## 检查清单

- [ ] 反馈以 contact 帧为锚点，不提前/延后
- [ ] 伤害/判定未被反馈层修改
- [ ] 起手、接触、冲击、收招各层职责清晰
- [ ] 每个事件有预算，连续命中有限流
- [ ] 颜色不是唯一信息；灰度/静音仍可辨
- [ ] 反馈不遮挡武器轨迹/起手/UI
- [ ] 轻/重/防御/破防/处决/特殊交互优先级明确
- [ ] 震屏不改变看向点/输入方向，有强度选项
- [ ] 音效/震动可辨且不叠加成噪音
- [ ] 固定步长审计通过；视觉接触有录屏/定格
- [ ] 真人试玩前不宣称「手感成立」

## 输出

- 反馈分层表：`references/feedback-layers.md`
- 事件预算模板：`templates/feel-spec.md`
- 审计记录：事件 / 期望 / 实际 / 证据 / 结论

## 反模式

- 按键瞬间就播命中反馈，伤害却晚到
- 每个命中都最大震屏/最长 hitstop
- 闪白遮住起手颜色/武器轨迹
- 音效堆满、震动常开，玩家靠猜
- 反馈层改伤害/判定/输入窗口
- 用静态截图证明打击感
- 用「感觉更好」代替固定步长与录屏
- 只做视觉，不做音频/震动/可访问性

## 交接

- 攻击时间轴/伤害/克制 → `game-combat-model`
- 动画资产/状态机/接触事件 → `game-animation-rig`
- 音频总线/持久化/headless → `godot-game-runtime`
- UI 可读性/字号/无障碍 → `ui-baseline`
- 验证计划/证据层级 → `validation-design`
- 项目验收/调参表 → `game-docs`

## 边界

- 不写具体项目的时长、幅度、帧数；由项目规范定义
- 不替代战斗模型、动画管线、UI 规范
- 不把主观偏好写成通用规则
- 不评价具体美术风格；只保证反馈可读、可验证、可关闭
