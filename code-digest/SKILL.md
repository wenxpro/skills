# 代码库梳理（演进 + 技术细节）

目标：演进可追溯、细节可复核、结论可写进文档。素材全在本地（git 历史 + 源码），不需要外部调研流程。

> 个人/团队偏好（证据标注格式、文档落点约定、细节粒度）在 `standards.md`，其他团队可整体替换。

## 何时使用

- 梳理项目演进：版本史、架构变化、决策沿革
- 汇总代码技术细节：模块职责、核心机制、数据结构、依赖
- 文档与代码现状不一致时，以代码为准核对
- 新成员或新文档需要理解代码库全貌

不适用：外部生态/竞品调研（用 `topic-research`）、多文档交叉引用审核（用 `docs-audit`）、分期规划（用 `roadmap-planning`）、实现跟踪（用 `implementation-track`）。

## 操作顺序

1. 界定任务
2. 建演进时间线（git 历史 + 语义记录）
3. 按模块读源码提取细节（文档先行）
4. 防遗漏、防过时与决策核对
5. 输出结论

## 第一步：界定任务

动手前回答并写下来：

1. 梳理范围？（整个项目还是某模块）
2. 结论写进哪里、给谁看？
3. 时间盒？

范围没界定就开始读，容易读不完或抓错重点。

## 第二步：建演进时间线（git 历史 + 语义记录）

1. `git --no-pager log` 扫全量 commit，按主题归类（功能、修复、重构、迁移）
2. **语义记录双源**：实现日志、变更记录、changelog 是比 commit 更语义化的演进来源——git 记录「发生了什么」，这类记录解释「为什么这么改」（本项目具体记录见 `standards.md`）。仓库有此类记录时并入时间线，每条附 commit 号或记录出处
3. 识别阶段：初版 → 扩展 → 重构/收敛，大版本边界看 tag 与破坏性变更 commit
4. 旧文档与当前文档对比，识别已过时描述（文档讲的是旧架构，代码已演进）
5. 输出时间线表：阶段、时间、关键变化，每条附 commit 号或记录出处可复核

演进以 commit 为准，不凭记忆；原因以语义记录为准，不猜。

## 第三步：按模块读源码提取细节（文档先行）

1. **文档先行**：若仓库有就近文档（包 README / DESIGN.md），先读文档建立索引（模块清单、职责边界、验收状态），再读源码；文档与代码冲突处，就是防过时核对要标记的过时点
2. 先列模块清单（目录/包结构），再逐模块读：职责、核心机制、数据结构、依赖、边界情况
3. 入口优先：main / CLI / 对外 API 先读，再深入实现
4. 技术栈判定以依赖清单为准（同 `topic-research` 的规则）
5. **测试是行为契约**：梳理机制细节时，测试用例比实现更能确认「实际行为」——读测试验证理解，必要时跑测试确认；实现与测试冲突时，先跑测试确认当前真实行为，以实测为准并标注（测试过时同样要标注）
6. 每个关键细节标注出处：文件路径 + 行号，读者能直接复核

## 第四步：防遗漏、防过时与决策核对

1. 模块清单 vs 已覆盖清单对照，漏的补读
2. 文档已有描述 vs 代码现状对照，不一致以代码为准，标注过时
3. **决策核对**：项目有编号决策体系时（编号清单见 `standards.md`），逐条核对代码落实情况，输出「已落实 / 偏离 / 未实现」三态——设计意图 vs 实现是比纯代码梳理更高一层的核对维度
4. 汇总数字（「共 N 个模块」「N 个事件」）实际数一遍，不轻信已有记录

## 第五步：输出结论

输出带证据标注的内容（格式见 `standards.md`）：

1. **演进时间线**：阶段、关键变化、commit 号
2. **技术细节**：模块职责与机制，每条带文件路径 + 行号
3. **过时与偏离清单**：文档与代码不一致处（注明当前代码实况）、编号决策未落实处
4. **未确认项**：写不出的标注「未确认」，不猜测代码意图

事实与判断分写，推断显式标注。输出先给用户确认，再按 `standards.md` 落点写入文档。

## 边界

- 只梳理、不擅自改代码或文档；改动前先确认
- 演进以 git 历史为准，不以记忆或口头描述为准
- **行为验证用隔离环境**：跑测试或运行程序时，配置目录指向临时位置，防止读到真实配置（凭据）并泄露；验证用的 key 不落命令历史、不入 git
