# Git 提交

按下面的流程处理一次提交。目标：每次提交一件事，message 可读、可检索、可追溯。多仓库时，每个仓库独立提交、独立推送、独立验证，不把多仓库当成一个原子事务。

## 何时使用

- 用户要求提交（「提交一下」「commit 这些改动」）。
- 功能、修复、重构、文档等阶段性完成后需要落一次提交。
- 一次任务同时改了多个独立仓库，需要按仓库分别提交和推送。

不适用：方案尚未确认的执行（先做设计）、文档内容审核（用 `docs-audit`）、改写历史或强制推送（先问用户）。

## 核心模型

- Git 提交是**仓库级**的；不存在跨仓库原子提交。
- 每个仓库有自己的分支、remote、凭据和工作区状态。
- 单仓库：一个提交只做一件事；内容混杂时拆成多个提交。
- 多仓库：先按仓库分组，再逐仓库提交；部分成功是正常结果。
- 不把 A 仓库的变更混进 B 仓库。
- 跨仓库变更前先确认接口版本与合并顺序；接口登记与集成计划见 `cross-project-integration`。

## 操作流程（单仓库）

1. **看变更**：`git status` 看文件清单，`git diff`（未暂存）和 `git diff --cached`（已暂存）看内容。
2. **分类**：按变更性质归类，一个提交只做一件事；默认按性质拆成多个提交，汇报时说明。
3. **检查无关文件**：`.DS_Store`、构建产物、依赖目录、日志等不应进仓库，自动排除并告知（必要时更新 `.gitignore`），不因此中断；用户的未提交工作不碰。
4. **生成 message**：按 `standards.md` 的格式生成。
5. **执行提交与推送**：`git add` + `GIT_EDITOR=true git commit -m "<message>"`，随后 `git push`（按项目远程配置）。

## 操作流程（多仓库）

详细步骤见 [references/multi-repo.md](references/multi-repo.md)。最小流程：

1. **预检**：列出所有仓库、路径、分支、remote、工作区和 owner。
2. **分组**：按仓库分组，不按时间或文件类型跨仓库混提交。
3. **排序**：有依赖时，被依赖的仓库先提交；使用方后提交；文档跟随代码仓库或紧接其后。
4. **逐仓库提交**：看变更 → 暂存明确路径 → 按 `standards.md` 提交 → 记录 hash。
5. **逐仓库推送**：推送 → `git ls-remote` 验证远端 → 记录状态。
6. **部分失败**：只重试失败仓库；已成功的不要重复提交；不声称“全部已推送”。

跨仓库一致性检查：

- 同一个任务/issue/ADR 的编号写进各仓库 commit message。
- 仓库 A 依赖仓库 B 的版本时，在总结里记录 B 的 commit hash。
- 代码仓库与文档仓库同时变更时，确保文档引用的是本次代码提交。
- 同一个变更不要在两个仓库重复实现；指定唯一 owner。
- 提交前确认接口登记表版本一致；只提交一侧会让下游失效。

## 边界

- 设计/方案确认后，提交与推送属于执行动作，直接做到目标，不逐次询问。
- 仅在 message 有歧义、变更混入用户未提交的工作、或需要不可逆操作（force push、删分支）时询问。
- 提交失败（pre-commit 钩子、lint 失败等）时报告错误，不擅自绕过。
- 写任务默认在独立 worktree 内完成；分支/worktree 的创建、合并、清理见 `worktree-workflow`。
- 本 skill 负责提交与推送；不负责设计决策、代码审查或验收状态更新。

## 反模式

- 把多个仓库当成一个原子提交。
- 一次 `git add -A` 扫过多个仓库。
- 推成功一个仓库就汇报“全部完成”。
- 把用户未提交的工作混进本次提交。
- 不同域名共用同一套凭据，失败后反复重试。
- 用 force push 处理部分失败。
- 不验证远端就宣布推送成功。
- 文档和代码同时改，却不互相引用。
